  ## A. Donor Defects: Types Implementing java.util.stream.Stream

  In donor commit b9f114a3, the author attempted to turn domain values, bags, and request attributes
  directly into java.util.stream.Stream implementations. This breaks the fundamental contracts of both the
  Java Stream API and domain entity models.

  ### 2. What Breaks When a Bag is Iterated Twice

  • Stream Contract vs. Iterable Contract Collision:
      • java.util.stream.Stream is strictly single-use. Javadoc states:
      "A stream should be operated on (invoking an intermediate or terminal stream operation) only once. A
      stream implementation may throw IllegalStateException if it detects that the stream is being reused."
      • Iterable<T> guarantees that iterator() can be invoked repeatedly to yield independent iterations.
      • In ValueStreamOfType.java:232:
        @Nonnull
        @Override
        default Iterator<VT> iterator() {
            return stream().iterator();
        }
      If stream() is backed by an actual pipeline or wrapped stream, the first iteration consumes the
      stream; the second iteration immediately throws IllegalStateException: stream has already been
      operated upon or closed.
      • Conversely, if stream() returns a fresh stream each time (e.g. BagOf.stream() returning values.
      stream()), the instance masquerades as a Stream but violates standard stream semantics (terminal
      operations do not exhaust the instance). Passing BagOf to methods expecting Stream<VT> causes
      unexpected behavior if the receiver assumes pipeline exhaustion.
  • Type Information Loss on Stream Operations:
      • In ValueStreamOfType.java:47-83, methods like filter(), map(), and limit() return standard JDK
      Stream<VT> or Stream<R>.
      • The moment a caller invokes bag.filter(...), the result ceases to be a SeqOf, BagOf, or
      ValueStreamOfType—all domain methods (valueType(), asBag(), asSet()) and multiset semantics vanish
      into a generic JDK stream.


  ### 3. equals and hashCode on Stream-Backed Types

  • java.util.stream.Stream intentionally defines identity equality only. Comparing streams via .equals()
  is an anti-pattern flagged by static analysis (e.g. ErrorProne StreamEquals, SonarQube S3958).
  • BagOf is a record holding Multiset<VT> values. Its equals() compares multiset contents.
  • Value implements SeqOf (and thus Stream), but its equals() compares underlying scalar values (LocalDate,
  Long, etc.).
  • ValueStream and ValueStreamOfType declare no equals/hashCode, falling back to Object reference identity.
  • When domain collections implement Stream, callers holding a Stream<VT> reference who call .equals() or
  store it in a HashSet/HashMap encounter either reference identity or broken symmetry.

  ### 4. Bag Multiplicity and Cardinality Violations

  • XACML bags are multisets (duplicates must be preserved for bag size, designator resolution, and bag
  functions).
  • In b9f114a3:SeqOf.java:47-50:
    @Nonnull
    @Override
    default Optional<VT> asSingle() {
        return findFirst();
    }
  asSingle() calls findFirst(). If a bag contains multiple elements (e.g. ["A", "B"]), asSingle() silently
  discards all elements after the first and returns "A".
  • This violates XACML 3.0 §A.3.5 / §7.3.5 and Design D7: single-value resolution requires
  requireExactlyOne(). If a bag has more than one value, it must evaluate to Indeterminate, not silently
  truncate.

  ### 5. Laziness Leaks (Late Exceptions and Context Capture)

  • In policy evaluation, evaluate(EvaluationContext context) is synchronous and bound to the lifecycle of
  a rule or policy.
  • If attribute resolvers, selectors, or designators evaluate to lazy streams rather than materialized
  query views:
      1. Delayed Exceptions: PIP attribute resolution errors (EvaluationException) are thrown when terminal
      operations run (e.g. inside higher-order functions or during response marshalling) rather than within
      evaluate().
      2. Context Escapes: The EvaluationContext may have already exited, and its MDC logging context
      cleaned (DefaultPolicyDecisionPoint.java:154 MDCSupport.cleanXacmlRequestId()), leaving downstream
      stream traversal without execution context.


  ### 6. Thread Safety

  • Stream instances are stateful and not thread-safe. Sharing a stream-implementing BagOf across
  concurrent rule evaluations causes ConcurrentModificationException or pipeline corruption.
  • In contrast, immutable multiset query views are completely thread-safe.

  ## C. Plan for Task 6.4

  ### 1. Minimal Query-View API (SeqOf<V, VT> / BagOf<V, VT>)

  SeqOf<V, VT> must stop extending java.util.stream.Stream. It becomes a lightweight query view over an
  immutable multiset of typed values:

    public sealed interface SeqOf<V, VT extends Value<V, VT>>
            extends ValueExpr<V, VT>, Iterable<VT>
            permits BagOf, Value
    {
        /** Returns a fresh, independent Stream over elements */
        @Nonnull
        Stream<VT> stream();

        /** Iterator support for enhanced for-loops: for (VT v : seq) */
        @Nonnull
        @Override
        Iterator<VT> iterator();

        /** Number of elements in sequence (with multiplicity) */
        int size();

        /** True if sequence contains no elements */
        boolean isEmpty();

        /** True if sequence contains the specified value */
        boolean contains(VT value);

        /** Resolves singleton; throws if size != 1 (Task 6.1 / D7) */
        @Nonnull
        VT requireExactlyOne() throws EvaluationException;

        /** Returns first element if present, or empty (where permitted by spec) */
        @Nonnull
        Optional<VT> first();

        /** Materializes as an immutable BagOf */
        @Nonnull
        BagOf<V, VT> asBag();
    }

  ### 2. Retirement / Replacement of ValueStream and ValueStreamOfType

  • Drop ValueStreamOfType.java and ValueStream.java's inheritance from Stream<T>.
  • Remove the 40+ proxy delegation methods to Stream.
  • Make Attribute implement Iterable<Value<?, ?>> and provide Stream<Value<?, ?>> stream() and
  Collection<Value<?, ?>> values().

  ### 3. Migration Order with Task 5.2 Bridge Types (from Run 043)

  1. Prerequisite (Task 5.2): BagOfValues bridges to BagOf, ValueExp bridges to ValueExpr, BagOfValuesType
  bridges to BagOfType. The reactor builds and passes with bridge adapters.
  2. Task 6.4 Implementation:
      • Sever SeqOf and ValueExpr from java.util.stream.Stream.
      • Update SeqOf to extend Iterable<VT>.
      • Update Attribute to stop implementing Stream.
      • Update call sites (AttributeStream.java:50, MultiRequestContext.java:237) to add .stream().
      • Fix Streams.extractTypeFromAny concatenation bug.
  3. Subsequent (Task 6.1 / 6.5): Replace single() / value() calls with requireExactlyOne() across function
  evaluation and attribute resolution.
