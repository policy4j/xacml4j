Verdict: REJECT. The single-check cache is sound for stable hash inputs, but the public model does not guarantee that all of these inputs are stable.

1. **P1 — Unconditional caching breaks equal-copy status lookup for supported mutable inputs.** Sites: `xacml-core/src/main/java/org/xacml4j/v30/policy/Rule.java:104`, `Policy.java:274`, and `PolicySet.java:327` (the latter two in the same directory).

   There are two concrete routes, requiring no hostile extension:
   - `types/Binary.java:55` duplicates a caller's `ByteBuffer` without copying its storage. `types/HexBinary.java:69` accepts that buffer. A literal in a Match is retained at `policy/Match.java:73` and hashed at `:179`; Target/AnyOf/AllOf do not freeze that hash. Thus a Rule's target can change its equality/hash inputs after construction. The same value can reach Policy/PolicySet through `CombinerParameter` (`policy/CombinerParameter.java:55`, `:67`).
   - `policy/BaseCompositeDecisionRuleDefaults.java:82` accepts any Object and stores it unchanged. Its ImmutableMap freezes entries, not the objects in them; `getValue` returns the object (`:52`), and `hashCode` reads its current hash (`:65`). For example, an ArrayList stored with `PolicyDefaults.builder().value("x", list)` remains mutable. Policy and PolicySet both include defaults in their cached folds.

   Reproducer sequence, derived from the source: build p; call p.hashCode(); update the buffer/list; build an equal copy q with the current contents; then insert p's status and retrieve it through q. Now p.equals(q) is true but their hashes differ, so `RootEvaluationContext.getEvaluationStatus(q)` (`:317`) can return empty. The update happens **before map insertion**: this is not the existing problem of modifying a key already in a map. Before AR, the D22 fold recomputed p's current hash at insertion.

   Consequently, the report's dismissal of Binary aliasing as solely pre-existing is incorrect for the newly cached Rule/Policy/PolicySet hashes. Existing caches in Apply, response expressions, or Entity do not protect the direct Match/defaults/combiner routes. Public Condition/Expression, custom FunctionSpec/combining algorithms, and custom composite children also have no enforced stable-hash contract; trusted extension code still needs its existing behavior preserved.

   **Fix:** make cache eligibility depend on transitive stable hash inputs, and retain the old D22 computation for graphs that cannot be established as stable. Keep eligibility work off the decision path. Alternatively, first establish detached immutable ownership for the affected inputs with approved API semantics; a shallow collection copy or volatile cache does not fix this. Add a compact public-behavior regression for equal-copy status lookup after a pre-insertion buffer/defaults update, checking pre-AR versus fixed behavior. This tests the new regression, not Binary's old aliasing mechanism.
