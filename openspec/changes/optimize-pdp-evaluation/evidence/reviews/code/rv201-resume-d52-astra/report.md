**P2 / D52-ASTRA-1 — The preparation proof accepts mutable custom parameter types and can replace Indeterminate with a boolean decision.**

Location: `xacml-core/src/main/java/org/xacml4j/v30/policy/function/FunctionSpecBuilder.java:328`–`329`; the cached proof is consumed at `xacml-core/src/main/java/org/xacml4j/v30/policy/function/impl/DefaultFunctionInvocation.java:207`–`208` and `:224`–`226`.

Trigger: build a fixed-arity boolean predicate through the public `FunctionSpecBuilder.param(ValueExpTypeInfo)` API using caller-owned mutable type metadata. Use two distinct custom `ValueType` instances, `expected` and `actual`, whose equality compares a mutable type key; both initially have key A, so the metadata is consistent during construction. The predicate parameter is `expected`. A data operand declares the stable bag type `actual.bagType()`; its `evaluate` changes only `expected` to key B and returns an empty bag of `actual`. Evaluate a canonical `all-of` or `any-of` Apply with runtime validation disabled. This requires no reflection, source changes or concurrent race.

The source trace is:

1. `FunctionParamValueTypeSpec.java:51` retains the supplied `ValueExpTypeInfo`; `:101` delegates each compatibility check to `DynamicType.isConsistent`, which calls that object's `equals` at `DynamicType.java:102`. The wrapper's final class does not make its supplied metadata immutable.
2. Candidate `FunctionSpecBuilder.java:328`–`329` accepts this wrapper and excludes only `DynamicType`. That check tests the dynamic sentinel at `DynamicType.java:87`–`88`; it does not prove immutability. `HigherOrderCall.java:75`–`76` proves parameter compatibility only at construction.
3. `HigherOrderCall.java:95` evaluates the operand, allowing its metadata change. The prepared value check at `DefaultFunctionInvocation.java:207` compares the actual bag with its captured bag type. Those remain identical; the predicate's changed parameter type is never consulted.
4. `HigherOrderFunctions.invokeSingle` enters `single` without `requireValidArguments`. An empty bag reaches `HigherOrderFunctions.java:121` and returns true for `all-of`, or false for `any-of`, without invoking the predicate.
5. The ordinary path still calls `requireValidArguments` (`HigherOrderFunctions.java:99` / `:172`). Its compatibility check at `:462` rejects key B versus key A, producing syntax-error with message `Invalid higher-order function arguments`. Its wrapper attributes that failure to the outer operator and emits its failure observation.

Reachable impact: `all-of` can produce TRUE where the existing path produces Indeterminate, and the outer failure status and observer event disappear. As a Permit rule's condition this can become Permit instead of Indeterminate{P}: `Condition.java:99`–`103` maps the boolean or exception to the condition result, and `Rule.java:151`–`169` maps that result to the rule decision. The same stale signature proof is used for binary calls in either bag position. The mismatch fallback cannot repair it because the returned operand type still matches the captured operand type.

Minimal correction: require a known immutable type representation before caching parameter compatibility. A narrow implementation is to admit canonical `XacmlTypes` scalar parameter types and standard any-value parameters, and canonical operand scalar/element types; keep custom metadata on the existing checked route. Alternatively, revalidate the signature whenever custom metadata participates. Checking only the parameter wrapper class or excluding only `DynamicType` is insufficient. Keep this a metadata restriction so D45 `Shared` expressions with canonical types remain eligible.

Regression test: add an outcome test using the public builder and the mutable-type operand described above. Reset both type keys before each case so construction and pre-operand validation succeed. Cover `any-of` and `all-of`, unary and binary calls, both bag positions, and runtime validation off/on. Assert the syntax-error status, exact message, outer `FunctionSpec` identity, one outer failure observation, one evaluation of each reached operand in order, and zero predicate invocations for the empty bag. A Permit rule wrapper should assert Indeterminate{P}. The mutation must occur during operand evaluation so the test also proves that enabling runtime validation does not merely reject an already-invalid setup before the relevant boundary.
