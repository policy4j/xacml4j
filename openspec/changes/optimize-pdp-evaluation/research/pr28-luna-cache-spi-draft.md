## Sourced library facts

### Guava `CacheBuilder`

The official Guava release on the fetch date is **33.7.2**. `CacheBuilder` provides `maximumSize`, `expireAfterWrite`, and opt-in `recordStats`; `Cache.get(key, Callable)` waits for a pending same-key load, rejects `null`, and does not modify observable cache state until the callable completes. Checked loader failures are exposed as `ExecutionException`; unchecked failures are wrapped. `Cache.stats()` returns zero-valued defaults unless statistics were enabled. These facts describe library capability, not the proposed adapter path: Guava's store should use explicit lookup/put under the shared xacml4j flight so uncacheable positive outcomes can reach flight callers without being retained. [Guava 33.7.2 release](https://github.com/google/guava/releases/tag/v33.7.2), [33.7.2 `CacheBuilder` Javadoc](https://guava.dev/releases/33.7.2-jre/api/docs/com/google/common/cache/CacheBuilder.html), [33.7.2 `Cache` Javadoc](https://guava.dev/releases/33.7.2-jre/api/docs/com/google/common/cache/Cache.html), fetched 2026-10-31.

The local parent POM already pins `com.google.guava:guava:33.7.2-jre` (`pom.xml:41,152-154`), so a Guava implementation need not introduce a new library dependency. The existing dependency is local evidence, not a claim that maintainers have approved its use for this feature.

### Caffeine

The official Caffeine release page identifies **3.3.1** as latest on 2026-10-31. Its official guides document `expireAfterWrite`, `maximumSize`, and opt-in `recordStats`. Synchronous `Cache.get(key, mappingFunction)` atomically computes a value, but if the function returns `null` or throws, later callers retry sequentially instead of sharing that failed/absent attempt. The FAQ also warns about recursive writes inside atomic computations. These behaviors support using Caffeine only as the positive-value store, outside the xacml4j flight callback. [Caffeine 3.3.1 release](https://github.com/ben-manes/caffeine/releases/tag/v3.3.1), [Population](https://github.com/ben-manes/caffeine/wiki/Population), [Eviction](https://github.com/ben-manes/caffeine/wiki/Eviction), [Statistics](https://github.com/ben-manes/caffeine/wiki/Statistics), and [FAQ](https://github.com/ben-manes/caffeine/wiki/Faq), fetched 2026-10-31. Wiki pages are mutable and not version-pinned; 3.3.1 is the release observed on that fetch date.

### cache2k

The official cache2k docs identify **2.6.1.Final**. `Cache2kBuilder` supports `expireAfterWrite(Duration)`, `entryCapacity`, and statistics are enabled by default; `Cache.get(key)` waits for a same-key configured load, while `peek` does not load. `Cache` implements `AutoCloseable`. Null values are prohibited by default, and a loader returning `null` throws rather than representing a miss. The exception documentation needs a qualification: the guide's general exceptions section describes caching/suppression with expiry, while its version-2+ resilience section and `ResiliencePolicy` Javadoc say that without a specified resilience policy only successful values are kept and `DISABLED_POLICY` is the default; `UniversalResiliencePolicy` enables exception caching/suppression when expiry is set. The proposed xacml4j adapter avoids the ambiguity by using no vendor loader and storing only eligible successful values. [cache2k 2.6.1.Final release](https://github.com/cache2k/cache2k/releases), [2.6.1.Final `Cache2kBuilder` Javadoc](https://cache2k.org/docs/latest/apidocs/cache2k-api/org/cache2k/Cache2kBuilder.html), [2.6.1.Final `Cache` Javadoc](https://cache2k.org/docs/latest/apidocs/cache2k-api/org/cache2k/Cache.html), [2.6.1.Final `ResiliencePolicy` Javadoc](https://cache2k.org/docs/latest/apidocs/cache2k-api/org/cache2k/io/ResiliencePolicy.html), and [2.6.1.Final user guide, §§2.9 and 9](https://cache2k.org/docs/latest/user-guide.html), fetched 2026-10-31. The user guide reports version 2.6.1.Final.

**Argon finding disposition:** P2-4 is accepted as a needed qualification, not as proof that cache2k retains exceptions by default. The reviewed draft said read-through *can* cache/suppress exceptions, which the guide does document; the default-policy detail was missing. The adapter recommendation below does not depend on either default because failures never reach a vendor cache loader.

P1-1, P1-2, P2-2, P2-3, P2-5, P3-1, and P3-2 are incorporated as source-supported design risks. P2-1's re-entry/deadlock risk is also incorporated as a reachable static risk through `ResolverContext.getEvaluationContext()`; no runtime cycle was exercised. Argon's suggested “run the nested loader inline” escape is not adopted: it can duplicate remote work, violate D35 coalescing, and recurse without bound. The draft instead leaves cycle detection and fail-fast mapping as an explicit design decision.

## Local observations from this source tree

- `PolicyInformationPointCacheProvider` is currently a `getContent`/`putContent` and `getAttributes`/`putAttributes` interface; its nested no-cache implementation is the builder default (`xacml-pdp/src/main/java/org/xacml4j/v30/spi/pip/PolicyInformationPointCacheProvider.java:29-83`; `PolicyInformationPoint.java:119-145`). `BasePolicyInformationPointCacheProvider` checks cacheability and timestamps but does not supply bounded storage, expiration maintenance, loading, or single-flight (`.../BasePolicyInformationPointCacheProvider.java:39-100`).
- Each descriptor carries a preferred TTL from `cache(int)` (`ResolverDescriptor.java:95-120`, `BaseResolverDescriptor.java:58-72`). D35 records that each descriptor needs its own cache, so one fixed `expireAfterWrite` value per cache is sufficient; it avoids per-entry varying TTLs within a resolver cache.
- `ResolverCacheKey` contains the resolver id and the content-equal context-key bags (`ResolverCacheKey.java:45-120`). A resolver context lazily resolves and memoizes its key (`ResolverContext.java:115-167`). A key-building path must not force early resolution of a resolver's dependencies or create a flight whose `ResolverContext` is shared across decisions.
- D27's current default PIP keeps one same-decision `DecisionSets` memo. For cacheable descriptors, it checks a known key's `DecisionSets` before the provider lookup, checks again after the lookup if the key became known there, and reconciles a cache candidate through `remember` before signaling a hit (`DefaultPolicyInformationPoint.java:182-227,238-273`). `forDecision()` shares the root PIP's provider, registry, and runner (`:74-90`). The proposed D35 path must keep that ordering: when the key is not already known, compute it only after a real cross-decision cache is selected; then check `DecisionSets` before querying/joining the D35 flight. Preserve the current no-cache path's lazy dependency reads.
- `ResolverContext.Default.getCacheKey()` resolves declared context refs, stores the resulting map and memoizes the key (`ResolverContext.java:149-166`). When all refs are absent the stored map is empty, while `resolveContextRef` retries `resolveAllContextRefs()` whenever that map is empty (`:191-197`). Thus an eager D35 key computation can resolve absent dependencies twice during one resolver call and can make the resolver result disagree with the empty-value key. For an active cross-decision cache, the key's dependency snapshot must be pinned for the owner resolver call even when all declared dependencies are absent; retain D27's retry behavior when no cross-decision key computation is requested.
- For descriptors declaring two or more optional context refs, `resolved(List)` inserts only present values and `getCacheKey()` passes only `resolvedKeys.values()` to `ResolverCacheKey.of` (`ResolverContext.java:149-166,218-231`; `ResolverCacheKey.java:74-81`). For example, `[USER=admin, ROLE=absent]` and `[USER=absent, ROLE=admin]` produce the same ordered bag array. This can collide in both the D35 store/flight and D27 `DecisionSets`, since both use `ResolverCacheKey`; retain declared slot identity/absence or bypass caching for these keys.
- D26's parallel resolver can return `Optional.of(incompleteSet)` after some members succeeded and another failed or timed out (`AttributeResolverDescriptor.java:184-200`). The current PIP returns that exact incomplete set to the current caller and does not put it into the cache (`DefaultPolicyInformationPoint.java:207-212`). Same-flight waiters must also receive that exact `Optional<AttributeSet>` so successful siblings remain usable and failed members can rethrow; only a complete set is retained.
- The existing SPI passes `ResolverContext` to get/put; `BasePolicyInformationPointCacheProvider` uses its descriptor and `context.getClock()` when applying TTL (`PolicyInformationPointCacheProvider.java:29-83`; `BasePolicyInformationPointCacheProvider.java:39-100`). A key-only replacement cannot directly support a compatibility bridge or logical clock expiry checks.
- D34 defines a hit as a value this decision did not compute; a waiter on another decision's load counts as a hit, while the decision that ran the resolver does not (`design.md:1416-1420`). Existing attribute code reports a hit only if `remember` selects the cache candidate (`DefaultPolicyInformationPoint.java:202-204`; `DefaultPolicyInformationPointForDecisionTest.java:226-260`). A value-only `Optional<T>` API cannot convey that provenance.
- `AttributeSet` and `ContentRef` retain creation timestamps, and current expiry checks compare them to `context.getClock().instant()` (`AttributeSet.java:57,165`; `ContentRef.java:43,54`; `BasePolicyInformationPointCacheProvider.java:86-99`). A library `expireAfterWrite` begins at cache insertion; it cannot replace admission and lookup checks against the value timestamp and evaluation clock.
- Resolvers can reach their `EvaluationContext` through `ResolverContext.getEvaluationContext()`. D27's flight ancestry guard is scoped to one evaluation handler (`DefaultEvaluationContextHandler.java:415-442`). Nested resolver lookups from inside a D35 loader can therefore re-enter a D35 flight, self-wait, or create a cross-decision wait cycle. A Caffeine atomic callback is an additional recursion hazard, but the proposed manual-store adapter avoids invoking remote loaders inside that callback.
- `DefaultPolicyInformationPoint.forDecision()` creates a view that shares the root provider; a future per-resolver handle must therefore be created/owned at root PIP scope, not per decision (`DefaultPolicyInformationPoint.java:74-90`). cache2k's cache is `AutoCloseable`, so a lifecycle hook and ownership rule are needed if its adapter is selected (cache2k `Cache` Javadoc, cited above).
- Resolver descriptors are typed as `ResolverDescriptor<AttributeSet>` or `ResolverDescriptor<ContentRef>` (`AttributeResolverDescriptor.java:62`; `ContentResolverDescriptor.java:35`). A resolver handle with both type-specific methods would carry an unused cache or force an untyped value store.
- D34 already has `resolverCacheHit` for a resolver answer supplied by the PIP cache (`DecisionObserver.java:177-184`). Its callbacks run synchronously on the deciding thread. D26 parallel resolver functions run on workers and report no observer callbacks (`design.md:843-869`). The cache SPI should not call application observers from a cache loader or background thread.

## Proposed API shape for approval

### Keep or replace the current SPI

**Recommendation: replace the get/put pair with a typed per-resolver cache factory and handle, while preserving a compatibility bridge if the maintainer requires existing provider implementations to keep working.** The current API has no way to express a shared in-flight outcome or hit provenance. The bridge and signatures remain open: passing `ResolverContext` into the new handle permits legacy get/put adapters and clock-based TTL checks; passing only `ResolverCacheKey` does not.

Candidate API, in the existing fluent style:

```java
public interface PolicyInformationPointCacheProvider {
    <T> ResolverCache<T> create(
        ResolverDescriptor<T> resolver,
        Predicate<? super T> retain,
        ResolverCacheConfig config);
}

public interface ResolverCache<T> extends AutoCloseable {
    ResolverCacheLookup<T> getOrLoad(
        ResolverContext context,
        ResolverCacheKey key,
        CheckedSupplier<Optional<T>> loader);
    ResolverCacheStats stats();
    default void close() {}
}

public record ResolverCacheLookup<T>(Optional<T> value, Source source) {
    public enum Source { STORE_HIT, FLIGHT_WAITER, LOAD_OWNER }
}
```

Names and exact signatures are proposals. `retain` is descriptor-specific: attributes retain only complete `AttributeSet`s; present `ContentRef`s are eligible. A flight completes with the exact resolver `Optional` or thrown failure for all callers that joined that attempt. Thus an incomplete set is returned to current flight callers but never stored; absence, failure, and timeout likewise end the flight without a store entry, and a later request retries. A flight stores only its key and outcome future; it must not retain or share the owner decision's `ResolverContext` or `EvaluationContext` with waiters. A `STORE_HIT` or `FLIGHT_WAITER` is an observer hit only if that candidate survives `DecisionSets.remember`; `LOAD_OWNER` is not a hit. Checked failures must preserve current PDP exception mapping.

The call path is part of the contract. First check whether a cross-decision cache is actually selected; with the no-cache provider, do not call `getCacheKey()` and keep resolver dependency reads lazy. On the enabled path, use an already-known key to check `DecisionSets`; otherwise compute the key once, pin the dependency snapshot for the resolver call even when all refs are absent, then check `DecisionSets` before reading or joining the cross-decision store/flight. After the lookup, reconcile with `DecisionSets`; report D34 hit only for the selected cache/flight-waiter candidate. This avoids a second resolution of all-absent refs and keeps task 30's decision-local answer first.

The current present-values-only `ResolverCacheKey` is not safe for multiple optional refs: preserve slot identity and absence in the key (recommend ordered `(AttributeReferenceKey, Optional<BagOfValues>)` entries) or explicitly disable cross-decision caching for such keys. The first option is recommended because it avoids collisions; any compatibility impact on `ResolverCacheKey` equality/serialization needs maintainer approval.

Resolver policy remains explicit in descriptor configuration: preserve `.cache(int seconds)` as the existing TTL spelling, and consider additive `.cache(Duration)` and `.cacheMaxEntries(long)` methods. If the size limit is intended to be global rather than resolver-specific, the PIP builder should supply a default and each resolver may override it. Recommend a finite entry-count default for every cacheable resolver; a weight limit needs a stable and comparable size measure for `AttributeSet` and `ContentRef`, which this tree does not currently provide.

**Cross-library recommendation:** make one xacml4j transient flight coordinator a mandatory shared layer for every adapter, keyed by `(resolver cache, ResolverCacheKey)`. It looks in the positive-only vendor store first; on a miss, `putIfAbsent` elects one owner and other decisions await that flight. The owner runs the resolver outside vendor callbacks and map-compute locks, completes the flight with its exact `Optional`/failure outcome, stores only a present value accepted by `retain` and not logically expired, then removes that flight in `finally`. An incomplete `AttributeSet` therefore reaches all callers already on that flight, while later requests retry. This is required by D26's successful-sibling behavior and D35 cross-decision sharing, not an optional cache2k workaround.

Nested resolver reads need a separate cycle rule. A loader must never join a flight in its own wait ancestry. Recommendation: detect same-flight re-entry and cross-flight wait cycles and fail fast with the existing resolver/evaluation failure mapping; do not silently run a second remote load inline, because that would violate coalescing and could recurse without bound. The exact cycle signal and cross-decision detection mechanism remain for maintainer review.

The library's `expireAfterWrite(ttl)` is only a storage lifetime bound, measured from insertion. Preserve logical TTL semantics separately: before admission and on every hit, compare the `AttributeSet`/`ContentRef` timestamp plus descriptor TTL with the current `ResolverContext.getClock()`; reject/remove an expired value. This handles old timestamps, slow remote loads, and synthetic evaluation clocks. Do not restamp on a hit. Keep the original timestamp so D37 can calculate remaining freshness.

### Placement, discovery, timeout and observer integration

- Proposed packaging: keep the public SPI/locator and Guava provider in `xacml-pdp` (Guava is already present); add optional modules tentatively named `xacml-pdp-cache-caffeine` and `xacml-pdp-cache-cache2k`. Use `com.github.ben-manes.caffeine:caffeine:3.3.1`; cache2k would compile against `org.cache2k:cache2k-api:2.6.1.Final` and provide `cache2k-core:2.6.1.Final` at runtime. These are research candidates from the official releases above, not approved dependencies or verified JDK 25 compatibility.
- Proposed one locator: `PolicyInformationPointCacheLocator` in xacml4j, discovering `PolicyInformationPointCacheProvider` implementations with JDK `ServiceLoader`. Existing `PolicyInformationPoint.Builder.cacheProvider(...)` selection should take precedence over discovery. No Artagon core locator is proposed. If no provider is installed, retain the current no-cache behavior. If multiple providers are installed with no explicit selection, recommend a clear ambiguity error instead of depending on class-path service order; the maintainer must choose the default-selection rule.
- D26's resolver timeout applies to parallel resolver functions, not universally to arbitrary synchronous backends. The loader must honor its configured remote deadline. A waiter's local timeout must not cancel a shared load used by other decisions, matching D27's “a waiting caller does not cancel the attempt.” If the backend attempt times out, remove the shared flight and cache no value. A successful completion after one waiter's local timeout raises a policy question: whether it may populate the positive cross-decision cache. Recommendation: if the underlying configured resolver operation itself was not timed out and completed successfully, it may be retained; if D26 reports that operation timed out or any attribute failed, reject the whole `AttributeSet` from cache. This distinction needs explicit tests and approval.
- D27 remains the first layer inside a decision: its memo can answer before the D35 store/flight. On a D35 miss, the D35 owner runs the resolver and D27's decision-local memo keeps the outcome under the resolved key. Never place `ResolverContext` or `EvaluationContext` in shared flight state. A D34 waiter is a cache hit only when its received candidate remains the decision's selected set/content.
- Preserve the original `AttributeSet`/`ContentRef` creation timestamp on every store hit and flight result. Logical expiry uses the evaluation clock and the original timestamp; the library's own expiry is only a secondary bound. Restamping would extend the declared lifetime and distort D37 remaining-TTL calculations.
- Keep D34's existing per-decision `resolverCacheHit` callback on the deciding thread. The cache result needs provenance (`STORE_HIT`, `FLIGHT_WAITER`, `LOAD_OWNER`) so a warm hit and cross-decision waiter can be reported, while a decision that ran the resolver is not. Expose a library-neutral immutable stats snapshot for aggregate hits, misses, loads, failures, evictions, and size; vendor counters differ and recording is optional for Guava/Caffeine. Recommend snapshots rather than callbacks from cache worker threads. Whether D34 needs a separate aggregate-statistics observer event remains open.
- Create one handle per resolver descriptor in the root PIP/provider lifetime; `forDecision()` views share those handles. Do not construct handles per decision. If cache2k is selected, expose a lifecycle path that closes its `AutoCloseable` caches when the owning PIP/provider closes; do not close a handle from `forDecision()` teardown. Whether `PolicyInformationPoint`, its provider, or a dedicated owner carries `AutoCloseable` remains a maintainer decision.
