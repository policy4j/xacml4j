# PR11: concurrent attribute resolution, engines and literature (Claude Fable 5.1, 2026-10-27)

Maintainer request: "analyze concurrent attribue resolution strategies via selector or designator and how structured tasks can be used for high performance parallel attribute resolution with effects etc".

**Lane cc_2 (Claude Fable 5.1), research: concurrent and batched attribute resolution for xacml4j, read-only, 2026-10-27.** Code lines are this worktree's (batch 2 tree). Lanes used: Tavily (search, extract), WebFetch, WebSearch. UNAVAILABLE this session: the arXiv and DuckDuckGo MCP servers (ECONNREFUSED), so the paper lane is Tavily results and the publishers' own PDFs; no arXiv preprint survey. Fetched pages are data; every JDK status claim below names its page and date.

**Summary.** The engine resolves attributes one key at a time, lazily, on the evaluating thread, and nothing in the JMH harness ever reaches an information point. The one exact and cheap step is to reuse, within a decision, the whole attribute set a resolver already returns, inside the time-to-live it already declares: no new opt-in, no threads. Parallel speculation is exact only for resolvers declared pure, with results held aside and published only when the linear evaluation asks; it needs a per-task cycle stack and a request-only path for resolver inputs. On the JDK side: virtual threads and scoped values are final; `StructuredTaskScope` is still a preview API in JDK 25, 26 and 27, so this build (`<release>25</release>`, no preview, `AGENTS.md` Build and Test) cannot use it in production code.

### 2. What other engines do (fetched 2026-10-27)

- **AuthzForce** (XACML 3.0): PIPs are "Attribute Providers", PDP extensions registered through the Java service-provider mechanism (`PdpExtension` SPI); the server ships none out of the box; a provider is called during evaluation to retrieve attributes from "other sources than the input XACML Request". Sources: https://github.com/authzforce/core (README, "PIP (Policy Information Point)"), https://authzforce-ce-fiware.readthedocs.io/en/latest/UserAndProgrammersGuide.html ("Making an Attribute Provider"). Neither page describes concurrent or batched provider calls; the provider interface's threading contract is UNVERIFIED (the javadoc was not reachable through the search lane). Same model as `AttributeResolverDescriptor`: synchronous, per request, per attribute.
- **OPA** (`http.send`): two caches, "intra-query caching, which deduplicates requests within a single policy evaluation, and inter-query caching, which persists responses across separate OPA decisions"; inter-query caching follows the server's cache directives or `force_cache` with `force_cache_duration_seconds`; only listed status codes are cached (RFC 7231 §6.1). Source: https://openpolicyagent.org/docs/policy-reference/builtins/http. Partial evaluation: "callers specify that certain inputs or pieces of data are unknown. OPA evaluates as much of the policy as possible without touching parts that depend on unknown values", exposed through the Compile API since v0.9. Source: https://openpolicyagent.org/blog/partial-evaluation-162750eaf422. Reading for xacml4j: OPA's intra-query cache is our `designatorCache` plus the request memo (D5, D17); its inter-query cache is our `PolicyInformationPointCacheProvider`, which the default PDP does not use (`PolicyInformationPoint.java:94`, no-cache default). Partial evaluation is the "static key analysis" of strategy 3 done by the policy compiler: it tells the caller which inputs matter before the decision.
- **Cedar**: the engine never fetches; the application assembles an entity slice before `isAuthorized`. Level validation bounds how far policies dereference entities, and "level-based slicing ... guarantees an authorization request made using the sliced entity data will give the same result as an authorization request using all entity data"; "the exact implementation of this procedure will depend on how your entity data is stored, so the Cedar library doesn't provide an implementation". Source: https://docs.cedarpolicy.com/policies/level-validation.html. Reading: the whole attribute fetch is hoisted before evaluation, which is exact for Cedar because its evaluation has no observable effects and no fetch errors; XACML has both (§7.19.3 missing-attribute status, our resolved attributes in the response), which is why hoisting is not exact here (section 4).
- **Zanzibar**: "To minimize check latency, we evaluate all leaf nodes of the boolean expression tree concurrently. When the outcome of one node determines the result of a subtree, evaluation of other nodes in the subtree is cancelled"; "We apply a pooling mechanism to group reads for the same ACL check to minimize the number of read RPCs to Spanner" (§3.2.3); request hedging for tail latency (§3.2.7); snapshot reads at a zookie-bounded timestamp prevent the "new enemy" problem. Source: https://www.usenix.org/system/files/atc19-pang.pdf (USENIX ATC 2019). SpiceDB exposes the same choice per call: `minimize_latency`, `at_least_as_fresh`, `at_exact_snapshot`, `fully_consistent` ("explicitly bypasses caching, dramatically impacting latency"). Source: https://authzed.com/docs/spicedb/concepts/consistency. Reading: Zanzibar can speculate because a tuple read has no effect and every leaf read is idempotent at a snapshot; the cancellation is what a `Joiner` gives. Its consistency token is the model for "one snapshot per decision", which is also what D24/D25's acquired generation gives the policy side.
- **Literature** (Tavily lane; arXiv UNAVAILABLE): NIST SP 800-162 defines the Context Handler as the component that "manages the order of policy and attribute retrieval ... attributes may be retrieved in advance of an access request, or cached to avoid the delay inherent in retrieval at the time of the access request" (https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-162.pdf). Kohler and Schaad, "Proactive access control for business process-driven environments" (ACSAC 2008) and Kohler, Brucker, Schaad, "Access Control Caching Strategies: An Empirical Evaluation" (2010, https://logicalhacking.com/publications/kohler.ea-caching-2010/kohler.ea-caching-2010.pdf) compare static decision caches, SAAM (approximate recycling of decisions, not exact) and proactive pre-evaluation driven by process models: they prefetch decisions, not attributes, and only the static cache is exact. Stoller et al., "Fast Distributed Evaluation of Stateful Attribute-Based Access Control Policies" (DBSec 2017, https://www3.cs.stonybrook.edu/~stoller/papers/dbsec2017.pdf): distributed evaluation with multiversion timestamp ordering, "minimizing the number of messages on the critical path", for policies whose requests update state; it is the formal treatment of our "non-idempotent source" case. A 2022 paper on opportunistic attribute caches for fog ABAC (ResearchGate listing, secondary, https://www.researchgate.net/publication/360285160) states the premise: "the policy decision point must send an across-the-network attribute request for each policy evaluation, impacting ABAC latency".

### 3. What "effects" means for this engine

Everything a reordered or extra resolution could change, with where it happens:

- **The information point call itself.** A resolver is arbitrary code (`AttributeResolverDescriptor.java:74-95` wraps it; `DefaultPolicyInformationPoint.resolve`, `DefaultPolicyInformationPoint.java:72-101`, asks the matching resolvers in registration order and stops at the first value). A call to a rate-limited, metered, or stateful source is observable outside the PDP; a speculative call that the linear order would have skipped is a new effect.
- **The response.** Every bag a PIP returns goes into `designatorCache` (`DefaultEvaluationContextHandler.java:248`) and from there into the result's resolved attributes (`DefaultPolicyDecisionPoint.java:170, 243-267`; `Result.resolvedAttr` at 209, 219, 228). A speculatively resolved key the linear path never asked for would appear in the response.
- **Status and failure.** A PIP failure is thrown at the point of use as a processing error (`failed`, `DefaultEvaluationContextHandler.java:252-256, 326-329`); `Match.match` records it as the rule's status and returns Indeterminate (`Match.java:129-132`); a missing `MustBePresent` attribute sets the missing-attribute status (`AttributeDesignator.java:91-99`), the §7.19.3 path ("If MustBePresent is True, then a missing attribute SHALL result in Indeterminate", and the response MAY list the missing attribute, §7.3.5 and §7.19.3, OASIS errata01). Failures are not memoized (D5, `design.md:89`), so a second ask calls the PIP again.
- **Order and short-circuits.** `DenyOverrides.doCombine` returns at the first Deny (`DenyOverrides.java:73-77`), `FirstApplicable` at the first decision (`FirstApplicable.java:52-53`, through `DecisionCombiningAlgorithms.evaluateIfMatch`, 50-53), `OnlyOneApplicable` matches every child first (`OnlyOneApplicablePolicyCombiningAlgorithm.java:51-67`); `Target`, `MatchAnyOf` and `MatchAllOf` stop at the first Indeterminate (`policy4j-yeu3`, `policy4j-0972`). Annex C fixes this order for the standard algorithms. Which keys get resolved, and whether a failure is reached at all, depends on it.
- **The first-bag rule.** §7.3.5: "the PDP SHALL behave as if each bag of attribute values is fully populated in the context before it is first tested, and is thereafter immutable during evaluation" (OASIS errata01 text, fetched). Implemented by `designatorCache` (`DefaultEvaluationContextHandler.java:177-181`) and the request memo (182-183, D5, D17). A speculative result that reaches the context before the first test is allowed by this sentence; a result that differs from what the first test would have fetched is not.
- **The information point cache.** With a cache provider, a result set is stored per resolver and resolved context keys (`DefaultPolicyInformationPoint.java:82-85`, key `ResolverContext.java:142-153`) and served until `getPreferredCacheTTL()` elapses (`BasePolicyInformationPointCacheProvider.java:88-95`, declared by `cache(int ttl)`, `ResolverDescriptor.java:117`, or `cacheTTL()` of `@XacmlAttributeResolverDescriptor`, `XacmlAttributeResolverDescriptor.java:38`). The default PDP has no cache (`PolicyInformationPoint.java:94`; the JMH fixture says so explicitly, `PdpFixture.java:126`).
- **Time.** `ResolverContext.getCurrentDateTime()` reads the clock per call (`ResolverContext.java:133-135`, `EvaluationContext.java:137-138`); the default environment resolver (`ResolverRegistry.java:104-121`, `noCache()`) computes current-time, current-date and current-dateTime from it. A resolution moved earlier in the decision reads an earlier instant. Only the first-bag rule hides the difference, and only when the speculative bag is the one published.
- **Resolver inputs.** A resolver's context keys are resolved through the evaluation context (`ResolverContext.java:174-181`, `context.resolve(k)`), that is through the handler again, possibly through another resolver; the cycle guard is one `Deque` per handler (`DefaultEvaluationContextHandler.java:87, 133-137, 238-241, 266-270`), shared by every thread that touches the context (D5 allows a PIP to call back from another thread, `design.md:95-100`). Two threads resolving in parallel would see each other's keys on that stack and report false cycles: any parallel design needs a per-task stack.
- **Decision cache time.** A resolver may shorten the decision's cache time through `EvaluationContext.setDecisionCacheTTL` (`EvaluationContext.java:108-118`, read at `DefaultPolicyDecisionPoint.java:178`); no production code calls it (search of `xacml-core` and `xacml-pdp` main, tests only), UNVERIFIED whether any deployment's resolver does. A speculative resolution that is never used must not shorten it.
- **Logging, audit, metrics.** The correlation id lives in the SLF4J MDC of the evaluating thread (`MDCSupport.java:57`; resolver ids at 105); a resolver running on another thread logs without it unless the task copies the MDC. Audit is per decision after the result exists (`DefaultPolicyDecisionPoint.java:152-153, 172-174`), metrics per decision (186-196); neither sees individual resolutions.

So "no observable effect" for a resolver means: no effect outside the PDP (no side effect, no metering), the same bag or the same failure for the same key and the same resolved context keys at any instant within one decision (idempotent and time-stable), and nothing written to the context's cache time. That is a declaration only the resolver's author can make.

### 4. Strategies, ranked

**Rank 1. Reuse a resolver's whole attribute set within one decision (the batching the SPI already has).** A resolver returns every attribute it provides in one `AttributeSet` (`AttributeResolverDescriptor.java:79-85`); `DefaultPolicyInformationPoint.resolve` picks the asked attribute out of it and throws the rest away unless a cache provider stores it (`DefaultPolicyInformationPoint.java:76-92`); the handler memoizes only the asked key (248). Two designators served by one resolver cost two resolver calls per decision in the default PDP. Change: a decision-scoped memo of result sets keyed like `ResolverCacheKey` (resolver id plus resolved context keys), consulted before the resolver function, in the handler or in `DefaultPolicyInformationPoint` for the decision, for resolvers with `isCacheable()` true (`BaseResolverDescriptor.java:65-67`). Exactness: within the time-to-live the resolver itself declared, serving the second attribute from the first set is what the cache provider would do (`BasePolicyInformationPointCacheProvider.java:88-95`); a decision takes microseconds, so the set is never older than the declaration allows; §7.3.5 is kept (the first bag of each key is still the only one tested); §7.19.3 is kept (absence of an attribute in the set is "no value" as today, 93-96, and failures are not memoized); Annex C order is kept (nothing is resolved before the linear path asks). Resolvers with `cacheTTL` 0 (the default, `XacmlAttributeResolverDescriptor.java:38`, and the environment resolver's `noCache()`) are not reused: the author declared them fresh per call. Opt-in: none new; the existing `cache(int ttl)` is the declaration. Observable change: fewer resolver calls per decision for cacheable resolvers, none in responses. Measurement: needs the PIP corpus of section 5; nothing in the existing corpora calls a resolver.

**Rank 2. Speculative parallel resolution of pure resolvers, results held aside.** At the start of a decision, fork one task per candidate key whose every matching resolver (`DefaultResolverRegistry.getMatchingAttributeResolver`, `DefaultResolverRegistry.java:80-89`, matching does not depend on the policy being evaluated) is declared pure and whose context keys are empty or come from the request only (resolved the way D24 reads its key, `resolveEntity` and `Entity.resolve`, never through the handler). The tasks run on virtual threads (JEP 444, final); each writes its bag or its failure into a per-decision staging map. The handler's `resolve` (`DefaultEvaluationContextHandler.java:167-191`) consults the staging map after the request memo and before `doPipResolve`: a staged bag moves into `designatorCache` at that moment, a staged failure is thrown at that moment as `failed(key, e)` would, a key not yet staged is awaited (join of that one task) or resolved inline. Exactness: with the purity declaration, the bag or failure the task produced is the one the linear call would have produced at the point of use; the response gets a resolved attribute only for keys the linear path asked (publication on demand), so the resolved attributes, the statuses, the missing-attribute details and the short-circuits of Annex C are those of the linear path; a key never asked is never published, and its task's result is discarded with no effect, which the declaration guarantees. A pure resolver that fails once and succeeds on the second call is excluded by the declaration (same answer for the same inputs within the decision), so "failure not memoized" cannot be observed. Decision cache time: a staged task must not call `setDecisionCacheTTL`; the staging context passed to the task is a view that records the request instead of applying it, applied at publication. The cycle stack: tasks get their own stack (the per-task state goes with the task on an executor; `ScopedValue` inheritance applies only to `StructuredTaskScope` forks, JEP 506). Opt-in, two levels: the resolver declares itself, `@XacmlAttributeResolverDescriptor(..., pure = true)` next to `cacheTTL` (`XacmlAttributeResolverDescriptor.java:38`) and `AttributeResolverDescriptor.builder(...).pure()` next to `cache(int)` and `contextRef(...)` (`ResolverDescriptor.java:117, 131`); the PDP enables the fan-out, `PolicyDecisionPointBuilder.speculativeResolution(Executor)` in the style of `pip(...)` (`PolicyDecisionPointBuilder.java:121`), default off; with the flag off nothing changes. Observable change: wall-clock latency of a decision bounded by the slowest speculated resolver instead of the sum; extra calls to pure resolvers for keys the linear path did not reach (declared effect-free); MDC fields absent in those resolvers' log lines unless the task copies the MDC (`MDCSupport.java:57`). Costs: one task per key per decision (allocation, scheduling), a staging map per decision; worth it only when resolver latency is far above the decision's CPU time (a 127 µs full scan on synthetic:1000 versus a 1 ms network resolver). Measurement: section 5.

**Rank 3. Static key analysis of the policy tree, as the feed of rank 2.** The candidate keys of rank 2 come from one walk per root policy and generation: `Match.getReference()` (`Match.java:103`) through `PolicyTreeVisitor.visitEnter(Match)`, `Condition.getExpression()` (`Condition.java:76`), `VariableDefinition.getExpression()` (78), `Apply.getArguments()` (242) with `VariableReference` followed to its definition (`Apply.java:144`); there is no expression visitor to reuse (`ExpressionVisitor` is empty, `ExpressionVisitor.java:32-34`; `AttributeDesignator.AttributeDesignatorVisitor` is a nested marker, `AttributeDesignator.java:123-127`), so the walk is a small switch over the expression classes. The walk also yields the "certain" subset: keys of the root target's first match are asked by every decision; everything after a possible short-circuit is "possible". Exactness: the analysis alone changes nothing; it only decides what rank 2 may speculate. Cached per generation with D24/D25's registry (one invalidation path). Opt-in: none beyond rank 2. Observable: nothing. Measurement: with rank 2.

**Rank 4. Cross-resolver batching (several resolvers in one round trip).** The SPI has no call that takes several keys; it would need a `BatchAttributeResolver` descriptor and a registry that groups candidate keys by resolver and source. Exactness as rank 2 (speculative, pure only). Larger API, same measurement; after rank 2 shows the gap between "parallel" and "one round trip".

**Rejected.** (a) Prefetch published straight into the context before combining: it changes the response's resolved attributes and turns a failure followed by a success into another decision (PR-astra P1, confirmed at `DefaultEvaluationContextHandler.java:248, 252-256`). (b) OPA-style inter-decision caching: already the cache provider SPI; wiring a provider is configuration, not engine work, and remains the first thing a PIP-heavy deployment should do. (c) Approximate recycling (SAAM) and pre-evaluated decisions (Kohler): not exact. (d) `StructuredTaskScope` in production code: preview in 25, 26, 27, one JDK per jar (JEP 12).

### 5. What is measurable with the existing harness, and what needs a new corpus

- **Existing harness, today's corpora: nothing about resolution.** `PdpFixture.open` builds the PDP with the default registry and no cache provider (`PdpFixture.java:126`); the default registry holds one resolver, the environment resolver (`ResolverRegistry.java:104-121, 138-140`); rsa2008 and synthetic requests carry every attribute their targets test (synthetic requests at `SyntheticCorpus.java:79-91`, targets at 144-147), so `doPipResolve` is never entered. D12 records "no PIP-heavy corpus exists yet" (`design.md:603`). Rank 1 to 4 therefore show nothing on the batch pair; only their fixed cost (a staging map, an executor) would, and it is zero with the opt-ins off.
- **The corpus to add** (`PolicyCorpusProvider`, registered as `xacml-jmh/README.md:149-151` says; the fixture needs one hook to pass resolvers into `PolicyInformationPoint.builder(...).registry(...)`, `PolicyInformationPoint.java:117-121`, because `PdpFixture` hard-codes the default registry): policies whose matches and conditions reference `k` attributes served by `m` resolvers, the requests carrying none of them; resolvers that sleep a parameter latency (`Thread.sleep(Duration)`, which on a virtual thread releases the carrier, JEP 444) and return deterministic bags; parameters: `resolvers` (1, 4, 16), `latencyMicros` (0, 100, 1000), `pure` fraction (0, 0.5, 1), `cacheTTL` (0, 30 s), `prefetch` (off, on); `@Threads(1)` and `@Threads(4)` as today. Report `avgt` per decision and `gc.alloc.rate.norm`; a resolver-call counter inside the benchmark's own resolver (a harness counter, not a test) to show the call count per decision for rank 1 and the extra speculative calls for rank 2. Expected shape: rank 1 cuts calls per decision from the number of designators to the number of resolvers with no latency change per call; rank 2 cuts wall time from the sum of the latencies on the linear path to the maximum, at the price of calls to pure resolvers the linear path would not reach. These are expectations, not measurements.
- **Correctness proof before any measurement**: the conformance suites and rsa2008 through a PDP with the opt-ins on (they must give the same counts, since nothing is resolved from a PIP there), plus focused response-level cases: a pure resolver asked only by a child that `first-applicable` never reaches (no resolved attribute in the response, no status); a pure resolver that fails (the same Indeterminate and status as the linear path, at the same child); an impure resolver next to a pure one (never speculated); a resolver with request-only context keys and one with PIP context keys (the latter never speculated); `MustBePresent="true"` with a staged absence (the same missing-attribute status).

**Residual risk and UNVERIFIED.** AuthzForce's provider threading contract (javadoc not fetched). Whether any deployment's resolver calls `setDecisionCacheTTL` (no caller in this tree). The gains of ranks 1 and 2 are reasoned from latency arithmetic, not measured, because no corpus exercises a resolver. The JDK 27 `Joiner` changes are a proposal (JDK-8373610, JEP 533), not a delivered release, as of the fetched pages.
