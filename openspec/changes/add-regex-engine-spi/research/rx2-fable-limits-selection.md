## Answer

**Q5. All four bead 4.58 limits still apply to a linear-time engine, but two change their meaning.** RE2J has no DFA, so there is no DFA memory budget to configure. Program size becomes the limit that matters, and the repetition bound becomes a compile-size bound.

Repository facts, all SUPPORTED by the opened source:

- The limits and their defaults are at `RegExpFunctions.java:150-154`. The length checks are at lines 381-384, the deadline starts before translation and compilation at line 388, the repetition weight is checked before compilation at lines 392-395, the deadline wrapper reads the clock once per 1,024 input reads at lines 312-352, and a late result is discarded at lines 409-411. Every limit yields processing-error with one fixed message, lines 683-687. The requirement is `specs/request-limits/spec.md:120-134`.
- The deadline sees only work that reads the input. Bead 4.58 is that gap: `"(?:(?=)|(?=))".repeat(26) + "(?!)"` ran 2,092 ms on an empty input, `.beads/issues.jsonl:229` and `evidence/builds/084-regexp-residual-accepted/summary.md:18-26`. The repetition weight closes the counted-repetition part of that gap, `RegExpLimitsTest.java:111-128`.
- The JDK engine also has a recursion-depth failure that no limit models: JDK-5050507 "Pattern.matches throws StackOverFlow Error" is Closed, Won't Fix, for inputs longer than 818 characters with `^([a-fA-F]|\d)+$`, https://bugs.openjdk.org/browse/JDK-5050507, retrieved 2026-10-27. Today such an Error inside a function is caught by the Throwable handler at `FunctionInvocationFactory.java:74-77`, wrapped, and becomes processing-error with a null message through `DefaultFunctionInvocation.java:148-149` and `FunctionInvocationException.java:61-75`. By code reading, not executed.

RE2J facts, SUPPORTED by the re2j-1.8 tag sources at https://raw.githubusercontent.com/google/re2j/re2j-1.8/java/com/google/re2j/, retrieved 2026-10-27:

- Matching is a Pike NFA simulation. `Machine.java` allocates two queues sized `prog.numInst()` and a thread pool, and steps once per input code point. The README states the guarantee: "RE2 is a regular expression engine that runs in time linear in the size of the input" and "In the worst case, the java.util.regex matcher may run forever, or exceed the available stack space and fail; this will never happen with RE2/J", https://raw.githubusercontent.com/google/re2j/master/README.md.
- There is no DFA. The package listing at https://github.com/google/re2j/tree/master/java/com/google/re2j has Parser, Simplify, Compiler, Prog, Machine, Matcher and no DFA class; the README says RE2/J ports "the NFA-based Go implementation". The C++ RE2 budget, `max_mem` with `kDefaultMaxMem = 8<<20`, "Once a DFA fills its budget, it flushes its cache and starts over. If this happens too often, RE2 falls back on the NFA implementation", https://raw.githubusercontent.com/google/re2/main/re2/re2.h, has no counterpart in RE2J.
- Memory per compiled pattern is proportional to program size. The machine cache per RE2 instance is unbounded: "There is no attempt to limit the size of the cache, so it will grow to the maximum number of simultaneous matches", `RE2.java` comment on `put`. `Matcher.programSize()` is public and returns the instruction count.
- Counted repetition is expanded at compile time. `Simplify.java` rewrites `x{n,m}` into n copies plus nested optional copies, "x{2,5} = xx(x(x(x)?)?)?". `Parser.parseRepeat` rejects a single count above 1000 with "invalid repeat count", but there is no nested-product check, no nesting-depth check, and no program-size cap: `Compiler.newInst` still carries "TODO(rsc): impose length limit." So `(?:(?:(?:a{1000}){1000}){1000})` parses and then expands toward a billion nodes. Go closed exactly this in `regexp/syntax/parse.go` with `maxHeight = 1000`, `maxSize = 128 << 20 / instSize`, and `repeatIsValid(re, 1000)`, which bounds the product of nested repeat counts to 1000, https://raw.githubusercontent.com/golang/go/master/src/regexp/syntax/parse.go, retrieved 2026-10-27. RE2 C++ documents the same 1000 restriction, https://github.com/google/re2/wiki/Syntax.
- The deadline wrapper keeps working. `Matcher.reset(CharSequence)` feeds `MachineInput.UTF16Input`, whose `step` reads through `Character.codePointAt(str, pos)`, so a deadline-checking CharSequence is still read on every step. Cost: the literal-prefix fast path uses `String.indexOf` only when the input is a String or StringBuilder, `MachineInput.java` method `index`; a wrapper falls to the `charAt` loop. The compile step cannot be interrupted on either engine; the post-compile clock check at `RegExpFunctions.java:397-399` stays.
- The weight scanner is engine-specific. The requirement says the scanner reads quoting, escapes, and classes "as the regular-expression engine reads them", `spec.md:129-132`, and today's rules are the `java.util.regex` rules, `RegExpFunctions.java:449-493` and `502-681`. RE2J accepts `\Q..\E` but rejects `(?x)` comments with "invalid or unsupported Perl syntax", `Parser.parsePerlFlags`. RE2J's parse tree is package-private, so the SPI cannot walk it; a scanner per engine syntax stays necessary.

What each limit does per engine:

| Limit | Engine `jdk` | Engine `re2j` | Keep? |
| --- | --- | --- | --- |
| Pattern length | Bounds parse time and everything below | Bounds parse time and AST recursion depth in Simplify and Compiler, which recurse on sub-expressions | Yes, same default |
| Input length | Backtracking blow-up factor; recursion depth, JDK-5050507 | Linear cost bound: time is input times program size; the only latency control besides program size | Yes, same default |
| Deadline | Primary control for catastrophic backtracking; blind to work without input reads | Defence in depth only; linearity makes it unnecessary for correctness; costs the prefix fast path | Yes for parity, measure its cost |
| Repetition weight | Bounds empty-group repetition the deadline cannot see; 1,000,000 default fits a non-expanding engine | Bounds compile-time expansion and memory; RE2J checks single counts only | Yes, re2j default 1000 like RE2 and Go |
| Program size | No equivalent | New: cap `programSize()` after compile; re2.h cites 10,000 instructions as the Code Search limit | New knob for re2j |
| DFA memory | Not applicable | Not applicable, no DFA | No |
| Cache size | Per-thread LRU, only with `.cacheRegExps`, `RegExpFunctions.java:175-179` | Compiled patterns are thread-safe, machine pool is a Treiber stack; a shared bounded cache is possible | Yes, shared, bounded, times program-size cap bounds memory |

**Q4, statuses. Malformed yields syntax-error, unsupported yields processing-error, a limit yields processing-error, on both engines; today a malformed pattern yields processing-error with no message.**

Normative text, SUPPORTED by two lanes, Tavily extract and WebFetch at offset 190000, https://docs.oasis-open.org/xacml/3.0/errata01/os/xacml-3.0-core-spec-errata01-os-complete.html, retrieved 2026-10-27. Section 7.19 is titled "Exception handling" in errata01, and the status codes are Appendix B.8, not B.9:

- 7.19.1: "If the PDP attempts to evaluate a policy set or policy that contains an optional element type or function that the PDP does not support, then the PDP SHALL return a <Decision> value of Indeterminate. If a <StatusCode> element is also returned, then its value SHALL be urn:oasis:names:tc:xacml:1.0:status:syntax-error in the case of an unsupported element type, and urn:oasis:names:tc:xacml:1.0:status:processing-error in the case of an unsupported function."
- 7.19.2: "If a policy that contains invalid syntax is evaluated by the XACML PDP at the time a decision request is received, then the result of that policy SHALL be Indeterminate with a StatusCode value of syntax-error. If a policy that contains invalid static data-types is evaluated ... processing-error."
- B.8: syntax-error "indicates that some attribute value contained a syntax error, such as a letter in a numeric field"; processing-error "indicates that an error occurred during policy evaluation. An example would be division by zero."
- A.3.13: "The function specification SHALL be that of the xf:matches function with the arguments reversed [XF] Section 7.6.2." XF is XQuery 1.0 and XPath 2.0 Functions and Operators, 23 January 2007. Its 7.6.2 says "Unless the metacharacters ^ and $ are used as anchors, the string is considered to match the pattern if any substring matches the pattern" and "An error is raised [err:FORX0002] if the value of $pattern is invalid according to the rules described in section 7.6.1", https://www.w3.org/TR/2007/REC-xpath-functions-20070123/, retrieved 2026-10-27. Section 7.6.1 extends the XML Schema syntax and defines back-references: "A back-reference matches the string that was matched by the nth capturing subexpression".
- The spec's own practice separates the two codes the same way. Section 5.30: an AttributeSelector whose data type has no constructor returns syntax-error, while an error converting the XPath values returns processing-error. A.3.9: a substring that is not a valid URI returns processing-error.
- XACML 2.0 says the same with other numbers: 7.15.1 to 7.15.3 on pages 87-88, A.3.13 on page 124 cites "xf:matches ... [XF Section 6.3.15]", B.9 on page 130, https://docs.oasis-open.org/xacml/2.0/access_control-xacml-2.0-core-spec-os.pdf, 1 February 2005, read 2026-10-27. Both editions bind the function to xf:matches, not to the XML Schema pattern facet.

Today's behavior, by code reading:

- A limit gives processing-error with the fixed message, `RegExpFunctions.java:683-687`, pinned by `RegExpLimitsTest.java:525-529`.
- A malformed pattern throws `PatternSyntaxException` from `Pattern.compile` at `RegExpFunctions.java:396` or `:285`. Nothing in the class catches it. The Throwable handler at `FunctionInvocationFactory.java:74-77` wraps it, `DefaultFunctionInvocation.java:157-167` finds no EvaluationException in the chain, and `FunctionInvocationException.java:61-75` builds processing-error with a null message. The cause is dropped because `Status.Builder.error` discards its argument, `Status.java:252-255`. No test pins this; `PatternSyntaxException` appears in tests only at `RegExpLimitsTest.java:291` for an unrelated assertion.
- Unsupported constructs are not a category today. The jdk engine accepts a superset of the XF grammar, and the translation at `RegExpFunctions.java:722-801` maps `\p{Is`, class subtraction, and `$`; the XML Schema escapes `\i` and `\c` are not translated.
- A value type without a string form gives syntax-error through `SyntaxException.invalidDataTypeId`, `RegExpFunctions.java:139-140` and `SyntaxException.java:35-43`.
- RE2J cannot tell "unsupported" from "malformed": `\1` fails in `Parser.parseEscape` as "invalid escape sequence" with the comment "Single non-zero digit is a backreference; not supported", `(?=` fails as "invalid or unsupported Perl syntax", and `\p{IsBasicLatin}` fails as "invalid character class range" because `unicodeTable` knows categories and scripts only. Its `PatternSyntaxException` extends `RuntimeException`, not `IllegalArgumentException`. The classification must therefore happen in the SPI before the engine compiles, or the statuses will differ by engine for the same policy.

Recommended mapping, with each engine:

| Case | Today, jdk | Recommended, jdk | Recommended, re2j |
| --- | --- | --- | --- |
| Pattern invalid under XF 7.6.1, for example `(` or `a{2,1}` | processing-error, no message | syntax-error, fixed message, no pattern text | syntax-error, same |
| Pattern valid under XF 7.6.1 but outside the engine, for example `\1` | matches | not applicable | processing-error, message names the construct and the engine, never the input |
| XML Schema construct the engine cannot express, `\i`, `\c`, `\p{IsX}`, subtraction | translated or silently misread | processing-error for untranslated constructs; translate where RX1 shows a translation | same |
| Java-only construct outside XF, lookaround, possessive, `(?x)` | accepted, `(?x)` rejected as a limit | keep accepting as a documented engine extension; log a portability warning at policy load | syntax-error, as re2j reports it |
| Limit: length, weight, program size, deadline | processing-error, fixed message | unchanged | unchanged, re2j adds program size |
| Engine Error, StackOverflowError or OutOfMemoryError | processing-error, null message | processing-error with the fixed limit message, caught at the engine boundary | same |

Reasoning for the two contested rows. A malformed pattern is an attribute value with a syntax error in the B.8 sense, and XF treats it as the dynamic error FORX0002; the pattern comes either from a policy literal, which is 7.19.2 invalid syntax, or from a request attribute, which is still B.8. An unsupported construct is well-formed under the grammar XACML mandates; the PDP, with this engine, cannot process the function on that value, which is the 7.19.1 processing-error case for functions. A limit is a resource decision of the PDP, like division by zero in B.8. Changing the malformed case from processing-error to syntax-error is a behavior change without a conformance consequence: every regexp fixture uses plain patterns such as `read|write` at `xacml3.0-ct-v.0.4/IIB008Policy.xml:32`, `J.* Hibbert` at `IIC056Policy.xml:15`, and `   This  is n*o*t* *IT!  ` at `IIC168Policy.xml:12`, and no fixture under `rsa2008-interop/` uses a regexp function; `rtk rg -l 'regexp-match'` over the resources tree lists 22 files, all under the two OASIS directories. The characterization tests the proposal asks for will pin processing-error first; the delta spec must then state the new status deliberately.

**Q4, engine selection.** The plumbing decides which options are real:

- The regexp functions are static methods registered by class in `XacmlDefaultFunctions.java:40-48`. The function provider is bound when a policy is loaded, by the repository or unmarshaller: `PolicyRepository.java:204-216`, `XacmlPolicyUnmarshaller.java:68-69`, and the static default at `MarshallingProvider.java:47-49`. `PolicyDecisionPointBuilder.java:46-161` has no function option.
- The only per-call path from PDP configuration into a function is the context parameter, `RegExpFunctions.java:67`, created per request at `PolicyDecisionPointContextFactory.java:168-192` from factory fields. Child contexts delegate each setting explicitly, `DescendantEvaluationContext.java:115-116, 120-121, 235-236, 275-276`, so a new accessor needs a delegation there.
- Instance providers exist: `FunctionProviderBuilder.fromInstance` at `:157-166`, and `JavaMethodToFunctionSpecConverter.java:86` accepts non-static methods when an instance is given. Duplicate function identifiers across providers throw, `BaseFunctionProvider.java:117-128`, so a second provider cannot override the six functions while the class-based registration stays.
- ServiceLoader precedents: `FunctionProviderBuilder.java:64-70` and `MarshallingProvider.java:72-77`, keyed by media type with first-wins on duplicates.
- A cautionary precedent: the builder's `xpathProvider` at `PolicyDecisionPointBuilder.java:134-139` is stored at `PolicyDecisionPointContextFactory.java:105` and never read; `rtk rg` over `xacml-pdp/src/main` finds no consumer.
- The limits are JVM-global and frozen at class init, `RegExpFunctions.java:171-179`, the only `System.getProperty` use in production code. An invalid value fails class initialization, `078-regexp-limits/summary.md:33-36`.
- `RegularExpressionFunctionsTest` calls the functions with a Mockito context and `verifyNoMoreInteractions` at lines 85, 96, 106, and 122; an engine lookup on the context changes those tests.

## Options and recommendation

Status mapping choices:

- S1, keep processing-error for malformed patterns. Cost: none. Risk: an author's typo and a resource limit look alike to the PEP. Test: a characterization test pins today's status.
- S2, syntax-error for malformed, processing-error for unsupported and for limits, same on both engines. Cost: a construct classifier for the XF 7.6.1 grammar in the SPI, and a delta to the request-limits requirement. Risk: a classifier gap lets an engine exception through; map any engine `PatternSyntaxException` that slips through to syntax-error so the gap is safe. Test: engine contract tests run the same table of patterns against both engines and assert identical status codes and messages; the OASIS suites stay green. Recommended.

Engine selection options:

- A, system property such as `org.xacml4j.regex.engine`, resolved by ServiceLoader name at class init. Cost: smallest; matches today's limit properties. Risk: one engine per JVM, frozen at class load; tests need a forked JVM; an unknown name breaks every function through `ExceptionInInitializerError`, as the limits do today. Test: a forked JVM with the property set uses the engine.
- B, `PolicyDecisionPointBuilder.regexEngine(...)`, carried to functions through a new `EvaluationContext` accessor with a default method. Cost: interface, root context, descendant delegation, context factory, builder, and the mock-context tests. Risk: the engine is unknown at policy load, so a literal pattern cannot be compiled once at load; the cache must be keyed by engine and pattern at evaluation time; the dangling `xpathProvider` shows how easily a builder option stays unwired. Test: two PDPs over one repository, `jdk` and `re2j`, give true and processing-error for `(a)\1`.
- C, engine bound into an instance-based regexp function provider, selected on `FunctionProviderBuilder` and surfaced on `PolicyRepository.Builder`. Cost: `XacmlDefaultFunctions` builds the regexp provider as an instance instead of by class; the static `matches(String, String)` at `RegExpFunctions.java:362` stays as the jdk convenience; the limits move onto the instance. Risk: selection is per repository, not per PDP, so a PDP with two repositories can mix engines; code that builds `FunctionProvider.builder().withDefaultFunctions()` gets the default engine unless it asks; the static `funcSystemProvider` at `MarshallingProvider.java:47-49` needs a default source. Benefit: the engine is known at load, so `Apply`, which already inspects arguments at build time at `Apply.java:159-187`, can compile a literal first argument once, and the mock-context tests stay as they are. Test: a repository built with `re2j` compiles its literal patterns with re2j, visible through `programSize()`, and a PDP over it returns the statuses of the table; the conformance suites run twice by swapping the provider.
- D, ServiceLoader name as the discovery mechanism under A, B, or C: a `RegexEngineProvider` with a name, `jdk` built in, `re2j` from `xacml-regex-re2j`. Risk: two providers with one name on the classpath; recommend fail fast like `BaseFunctionProvider.java:117-128`, not first-wins like `MarshallingProvider.java:76`; a missing module must fail when the provider is built, not at the first match. Test: a duplicate name throws at build; `re2j` without the module throws at build.
- E, selection from the request or per evaluation only. Reject: the limits exist because the pattern is policy content, `RegExpFunctions.java:42-55`; the request must not choose the engine.
- F, separate function identifiers per engine. Reject: non-standard identifiers make policies non-portable.

Recommendation: C with D, and A only as the default source. The engine is a constructor argument of the regexp function provider, chosen by name through ServiceLoader, set on `FunctionProviderBuilder` and `PolicyRepository.Builder`, defaulting to the system property read when the provider is built rather than at class init, with `jdk` as the default. Limits are per engine instance from the same builder, with today's property names as defaults for compatibility; the re2j instance adds a program-size cap and lowers its repetition bound to 1000. Keep the deadline on both engines until the JMH lane measures the wrapper's cost on re2j. If the maintainer wants per-PDP selection, B is the fallback, at the price of compile-once at load.

Defaults proposed here, like the 078 defaults, need the maintainer's confirmation: re2j repetition product 1000, program size 10,000 instructions, shared cache 256 patterns.
