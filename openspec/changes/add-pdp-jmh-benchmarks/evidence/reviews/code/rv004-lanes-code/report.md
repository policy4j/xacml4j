## Findings

**1. Major.** `PolicyStoreLoadBenchmark.importXml` builds a new `PolicyImportTool` for every source, so one measured operation runs the uncached marshalling-provider discovery once per policy.
- Where: xacml-jmh/src/main/java/org/xacml4j/jmh/pdp/PolicyStoreLoadBenchmark.java:122-124 calls `repository.newImportTool()` inside the loop; checked. The tool's constructor calls `MarshallingProvider.discoverProviders()` (xacml-pdp/src/main/java/org/xacml4j/v30/spi/repository/PolicyImportTool.java:53-56; checked), which is a fresh `ServiceLoader.load(...).stream().map(p -> p.get())` scan on every call (xacml-core/src/main/java/org/xacml4j/v30/marshal/MarshallingProvider.java:72-77; checked). The harness caches the same discovery once in a static field (xacml-jmh/src/main/java/org/xacml4j/jmh/harness/Marshalling.java:36; checked).
- Why it matters: for `synthetic:100` one operation performs 101 classpath resource scans and 101 reflective provider instantiations that belong neither to the store nor to parsing. The score and its `gc.alloc.rate.norm` grow with corpus size for a reason D7 did not intend, and the pair `importXml` against `loadParsed` no longer isolates parse cost from store cost. D7 words the import as one tool per lifecycle: "through the production PolicyImportTool (repository.newImportTool())" (design.md:278; checked). Both lanes flagged it as a question for rv004 and rv005 (evidence/builds/011-lane-reports/summary.md:15-18; checked). Magnitude: UNVERIFIED, this lane may not run the jar; the unwarmed smoke shows 4.8 ms for nine sources (evidence/tests/008-fanin-functional-smoke/summary.md:24-25; checked) and cannot separate the two costs.
- Fix: hoist the tool. `PolicyImportTool tool = repository.newImportTool();` before the loop, then `tool.importPolicy(source.mediaType(), source::open)`. One discovery per lifecycle stays in the number, as D7 says.
- Test: a test store whose repository wrapper overrides `newImportTool()` and counts calls (the test package has forwarding and recording wrappers, `ForwardingPolicyRepository` and `RecordingPolicyRepository`, names from the file list, bodies not checked); one `importXml` call; assert one tool per operation.

**2. Minor.** `PolicyStoreLookupBenchmark.lookup` returns an `Optional`, so every operation allocates 16 bytes in the harness that the `cursor` control does not include.
- Where: PolicyStoreLookupBenchmark.java:104-107 returns `cursor.next().find(fixture.repository())`; checked. `LookupQuery.find` wraps the result in `Optional.ofNullable` (xacml-jmh/src/main/java/org/xacml4j/jmh/harness/LookupQuery.java:89-95; checked). After `open` every corpus lookup returns a rule (PdpFixture.java:268-291; checked), so the non-empty branch allocates on each call, and the value escapes into the Blackhole, so escape analysis cannot remove it.
- Why it matters: D11 makes `gc.alloc.rate.norm` the allocation record (design.md:368-371; checked) and D8 says a method returns "the found rule" (design.md:320-321; checked). With this code a zero-allocation store reads 16 B/op on `lookup` and 0 B/op on `cursor`, so the subtraction D7 sets up overstates every store by a constant.
- Fix: switch on `query.kind()` inside `lookup` and return the raw `CompositeDecisionRule` from `get`, `getPolicy`, or `getPolicySet`; null is a legal repository answer and JMH consumes it. `PolicyStoreLookupBenchmarkTest.rule(Object)` already accepts a raw rule (PolicyStoreLookupBenchmarkTest.java:128-137; checked), so no test changes.
- Test: no in-process test catches a 16-byte bias; a GC-profiler smoke of `lookup` can assert the floor after this fix and nit 6, and the task 4.2 summary should state the floor otherwise.

**3. Minor.** `DirectoryCorpus` reads every regular file in `policies/` and `requests/`, so hidden files fail late and with the wrong message.
- Where: DirectoryCorpus.java:122-130 lists and sorts all regular files; checked. A `.DS_Store` in `policies/` becomes a `PolicySource` (lines 108-111; checked) and fails in `PdpFixture.parse` with the unmarshaller's `SyntaxException` (PdpFixture.java:134-140; checked), not with a corpus message. The spec lists manifest errors and says nothing about hidden files (spec.md:176-187; checked), so this is robustness, not a violation.
- Fix: in `files()`, filter out `Files.isHidden(file)` or names that start with a dot.
- Test: in `DirectoryCorpusTest`, write a `.DS_Store` into both subdirectories of the valid corpus and assert two policies and three requests.

**6. Nit.** The snapshot store allocates on each unconstrained `getPolicy` and `getPolicySet`, and its load is quadratic.
- Where: SnapshotPolicyRepository.java:172-174 uses `versions.lastEntry().getValue()`; checked. `TreeMap.lastEntry` exports a new entry and the `unmodifiableNavigableMap` wrapper at line 163 wraps it again (JDK behavior from source knowledge, not checked in this session); `latest` then returns an `Optional` (lines 73, 78; checked). - Why it matters: D10 makes this store the lean comparator, "both built-in stores answer get by a map lookup" (design.md:359-360; checked), and its allocation shows in the lookup numbers. The quadratic load is a property of copy-on-write, not a defect.
- Fix: `T last = versions.get(versions.lastKey())` and return `T` or null without an `Optional`; for the constrained path iterate `versions.descendingMap().entrySet()` once. Keep the copy-on-write.
