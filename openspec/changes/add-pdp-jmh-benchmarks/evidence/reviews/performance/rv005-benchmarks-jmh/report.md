## Findings

**1. Major.** `importXml` builds one production import tool per source, so a measured operation runs the uncached `ServiceLoader` discovery of the marshalling providers once per policy. Carried from rv004 finding 1; the method consequence is spelled out here.
- Where: PolicyStoreLoadBenchmark.java:122-124 calls `repository.newImportTool()` inside the loop; checked. Each tool runs `MarshallingProvider.discoverProviders()` (PolicyImportTool.java:53-56; checked), a fresh `ServiceLoader.load(...).stream().map(p -> p.get())` on every call (MarshallingProvider.java:72-77; checked). D7 words it as one tool whose discovery is part of the number (design.md:278; checked).
- Why it matters for the method: the `importXml` score and its `gc.alloc.rate.norm` carry a per-policy term that is neither parse nor store cost, so the `importXml` to `loadParsed` difference that D7 sets up to isolate parse cost is wrong by n discoveries, and the corpus scaling of `importXml` is distorted. Magnitude: UNVERIFIED in this lane; the unwarmed smoke gives 4.8 ms for nine sources and 35 to 44 ms for 101 (score-table.txt:13-16; checked), which cannot separate the terms.
- Fix: hoist `PolicyImportTool tool = repository.newImportTool();` above the loop. One discovery per lifecycle stays inside the operation, as D7 says. After the fix, the operation still includes the production parser setup per source, see "What one operation includes" below; the baseline summary must say so.
- Test: as in rv004, a repository wrapper that counts `newImportTool()` calls, one operation, one call.

**2. Major.** The scaling command of the Benchmark Plan runs `request=all`, so it cannot give the per-request scores that D9 promises for scaling claims, and its score is a mix with three short-circuit requests.
- Where: the second command sets only `corpus` and `store` (design.md:450; checked), so `request` keeps its default `all` (PdpDecideBenchmark.java:63-64; checked), an equal-weight cycle of the seven synthetic requests (PdpFixture.java:183-186, PdpDecideBenchmark.java:146-158; checked). D9 states that a Deny request stops at its slot while the Permit and NotApplicable requests check all n policies, and that "run summaries report scores per request id for scaling claims" (design.md:339-342; checked); the engine returns at the first Deny (DenyOverrides.java:76-78; checked).
- Why it matters: with `request=all` JMH reports one score per corpus. For n policies that score is about (4n + 1 + n/2 + n) / 7 target evaluations, about 0.79 n, so a per-policy cost read from it is low by a fifth, and the three Deny requests contribute almost nothing at large n. The per-request numbers D9 asks for do not exist in that JSON at all.
- Fix: add `-p request=first-permit,first-deny,middle-permit,middle-deny,last-permit,last-deny,unknown-notapplicable` to the scaling command. JMH runs each value as its own trial, so the summary gets one score per request id: `last-permit` and `unknown-notapplicable` give the full-scan cost, `first-deny` the short circuit. Cost: 2 corpora times 7 ids times 3 forks times 10 s, about 7 minutes. Keep `request=all` in the default run as the mix, and label it as a mix.
- Check: the completeness script of D11 expects 14 result keys for that file.

**3. Minor.** The JIT that compiles the benchmark code is not chosen or recorded. The smoke ran on Oracle GraalVM with the JVMCI compiler enabled, so Graal, not HotSpot C2, produced its numbers.
- Where: the smoke's forks ran `graalvm-21.jdk` with `-XX:+EnableJVMCIProduct` and `vmVersion 21.0.6+8-LTS-jvmci-23.1-b55` (results-default.json:8-17; checked); the smoke summary names only "Oracle GraalVM 21.0.6+8.1 (HotSpot)" (summary.md:3; checked). The Benchmark Plan says "JDK 21" (design.md:444; checked) and AGENTS.md picks `jenv prefix 21` for every run, which is this GraalVM on this machine (command.txt:1; checked). D11 records "the exact JDK build" and "the JVM flags" (design.md:376-379; checked), which the JSON gives, but no artifact names the compiler.
- Why it matters: Graal and C2 inline, escape-analyze, and vectorize differently; numbers from the two are not comparable, and the later work of modernize-core-for-jdk28-valhalla runs on OpenJDK EA builds with C2. A baseline taken on Graal would be compared with C2 numbers by whoever reads the ledger later.
- Fix: decide once, in the plan: either an OpenJDK 21 build, or GraalVM with `-jvmArgs -XX:-UseJVMCICompiler` so C2 compiles. Record the choice in `env.txt` with `java -XX:+PrintFlagsFinal -version` filtered for `UseJVMCICompiler`, `EnableJVMCIProduct`, `MaxHeapSize`, `UseG1GC`, and write it in `summary.md`. BENCHMARKS.md's "same JDK build, the same flags" (BENCHMARKS.md:66-67; checked) then has a stated meaning.

**4. Minor.** Nothing checks a decision or a lookup after measurement starts, so a store that drifts during a trial gives fast and wrong lookup numbers.
- Where: the lookup and decision checks run once, inside `open` (PdpFixture.java:98-126, 268-291; checked). `lookup` returns whatever the store answers (PolicyStoreLookupBenchmark.java:104-107; checked); an empty `Optional` from a store that evicted or lost an entry is consumed at full speed. `decide` cannot drift through the store, because the reference resolver asks the store once per reference and never again (DefaultPolicyReferenceResolver.java:80-108; ReferenceCacheCharacterizationTest.java:72-94; checked), but it can drift through a `dir` corpus whose policies depend on the clock. `loadParsed` cannot drift silently, because `StoreSession.load` throws on a false `add` (StoreSession.java:49-58; checked); `importXml` can, because the production import tool ignores a false `add` (PolicyImportTool.java:78-79; checked; bead policy4j-d4as).
- Why it matters: the proposal's headline is any store, also from outside this repository (proposal.md:8-10; checked). The design's guarantee "a wrong store ... can never give numbers" is stated for setup time (design.md:72-75; checked), which is right; this closes the gap for the end of the trial at no cost to the operation.
- Fix: a public `PdpFixture.recheck()` that runs the private `check()` again, called from each `tearDown` before `close()`, so a changed lookup or decision throws and `-foe true` fails the run. The built-in stores cannot change, so the baseline is unaffected. For `importXml`, the fix is the bead, out of scope.
- Test: a test store that answers correctly during `open` and empties on a flag; after one `lookup`, `tearDown` throws and names the lookup.

**5. Minor.** `lookup` returns an `Optional`, a 16-byte harness allocation per operation that the `cursor` control does not include. **6. Minor.** The run record of D11 misses four things the numbers depend on, and the completeness check accepts a result without an error estimate.

The completeness check asks for "a finite score" (design.md:373-375; checked); the smoke JSON shows that one iteration gives `scoreError` and `scoreConfidence` of `NaN` next to a finite score (results-default.json:29-35; checked).
- Why it matters: the effective heap and collector change `gc.count`, `gc.time`, and so the average time; the JIT (finding 3) changes everything; with `-foe true` a failed trial aborts the run, and whether JMH still writes the partial JSON is UNVERIFIED in this lane, so the console output is the only sure record of which trial failed; a NaN error passes a "finite score" test.
- Fix: pass explicit `-jvmArgs "-Xms2g -Xmx2g -XX:+UseG1GC"` (or the flags the plan chooses) so the JSON's `jvmArgs` names them; add `-o <run>/jmh.log` to both commands; add `gc.count` and `gc.time` columns to the summary; make the completeness script require finite `scoreError` and 15 raw samples per result (3 forks times 5 iterations, results-default.json:49-53 shows the `rawData` shape; checked); record the CPU model with its core types (the smoke ran on a Mac, command.txt:1; macOS may schedule a fork on efficiency cores, general knowledge, not checked) and the per-fork spread from the log.

## Checked and found correct

State scopes and setup order:
- The fixture is `@State(Scope.Benchmark)`, one per trial, shared by all threads; the cursors are `@State(Scope.Thread)`, one per thread (PdpDecideBenchmark.java:49, 140; PolicyStoreLookupBenchmark.java:49, 124; PolicyStoreLoadBenchmark.java:49, 147; checked). A cursor's trial setup takes the benchmark state as a parameter (PdpDecideBenchmark.java:146-150; checked), so JMH initializes the benchmark state, with its trial setups, before the cursor reads `selected()` or `lookups()`. That JMH orders dependent states this way is JMH internals, not checked in source; the cursor tests and the smoke show the cursors populated (PdpDecideBenchmarkTest.java:119-143; checked).
- The two trial setups of each class tolerate either order (PdpDecideBenchmark.java:69-95; checked). Which order JMH uses: not checked.

Nothing is prepared inside a measured method, as BENCHMARKS.md asks (BENCHMARKS.md:42-43; checked).

Dead-code elimination and constant folding:

- Inputs are non-final instance fields of state objects read on each call: `fixture`, `items`, `index` (PdpDecideBenchmark.java:66-67, 143-144; checked). `index` advances on every call, so no two consecutive operations fold to the same constant. The same request object recurs every n operations; the PDP keeps nothing per request: the decision cache is `NoCachePolicyDecisionCache` by default (PolicyDecisionPointBuilder.java:66-72; checked) and returns null (NoCachePolicyDecisionCache.java:33-40; checked); the PIP has no cache (PdpFixture.java:113; checked).

Modes, units, forks:

The D7 premise:
- A second `decide` of a request asks the store nothing; the first asks it once per reference (ReferenceCacheCharacterizationTest.java:55-94; checked), because the resolver caches every resolved reference without a bound (DefaultPolicyReferenceResolver.java:55-58, 92-100; checked). So `decide` measures the PDP with a warm reference cache, never the store. The smoke's decide gaps between stores, 112 against 118 µs on `rsa2008` and 2.84 against 3.62 ms on `synthetic:1000` (score-table.txt:6-12; checked), are therefore noise of single unwarmed iterations, not a store effect; they show the noise level that the baseline's 15 samples per result must beat.

No random number runs on the path: the histogram is created and never updated (DefaultPolicyDecisionPoint.java:71, 85; checked), the counters are `inc()` calls (lines 173-183; checked).

## What one operation includes

The baseline summary must say this for each benchmark, because the numbers are read as "store cost" otherwise.

- `decide`: one `decide` of the next request of the mix: MDC put and remove of the PDP id and of the request id, four `ThreadContext` operations (DefaultPolicyDecisionPoint.java:94-107, 134-169; MDCSupport.java:56-70; checked; with log4j2's default copy-on-write context map each is a map copy, log4j2 behavior from knowledge, not checked, and the module sets no `log4j2.garbagefreeThreadContextMap`); a correlation id string, a context object, the handler chain of `MultipleResourcesHandler` for a single request (PolicyDecisionPointContextFactory.java:112-116; PolicyDecisionPointBuilder.java:117-119; MultipleResourcesHandler.java:71-79; checked); a new evaluation context with a `Duration` and a handler (PolicyDecisionPointContextFactory.java:167-191; checked); the evaluation itself with the reference cache warm; the result and response objects. For `rsa2008` the `environment:locality` attribute comes from the request, no clock resolver runs (XacmlPolicySet-02f-emergency.xml:31-87; checked).
- `lookup`: see the control above. On the in-memory store a reference query streams, collects, and takes the maximum; an exact query is one map lookup. On the snapshot store an unconstrained reference query exports a map entry twice and wraps an `Optional` (SnapshotPolicyRepository.java:172-174; rv004 nit 6).
- `loadParsed`: a new context string with a sequence number (PdpFixture.java:307-310; checked); the store's constructor; for `in-memory` an executor service that never starts a thread and two concurrent maps with initial capacity 2048 (InMemoryPolicyRepository.java:58-71; AbstractPolicyRepository.java:66-72; checked), whose tables are allocated at the first put, about 16 KB each with 4096 slots by the JDK's sizing, JDK formula from knowledge, not checked; one `add` per policy, each walking the policy tree with the combining-algorithm validator (AbstractPolicyRepository.java:213-243, 293-311; checked); for `snapshot` one copy of the id map per add, twice (SnapshotPolicyRepository.java:92-105, 159-165; checked), hence quadratic in the corpus size and 30 times the in-memory number at n=100 (score-table.txt:19-20; checked); `close`, a no-op for both built-in stores.
- `importXml`: all of `loadParsed` plus, per source, one `ByteArrayInputStream`, the discovery of finding 1, a JAXB `Unmarshaller` and a new secured SAX parser from `SAXParserFactory.newInstance()` (BaseJAXBUnmarshaller.java:82-86, 139-146, 162-171; checked; the JAXP factory lookup is itself a service lookup, from knowledge, not checked), the parse, the object-model build, and the `add`. After the hoist, the number is "production import", dominated by parser setup and parsing, not by the store.
