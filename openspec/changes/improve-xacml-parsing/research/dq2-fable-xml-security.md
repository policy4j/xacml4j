## Q1. JDK 21 and JDK 25 XML processing limits, their defaults, the enforcing properties, and the configuration file

**Answer.**

1. The limits are JDK implementation properties with the prefix `jdk.xml.` (legacy `http://www.oracle.com/xml/jaxp/properties/...` names deprecated since 17). They are "Security Properties": when `XMLConstants.FEATURE_SECURE_PROCESSING` (FSP) is true, the value in the "Enforced" column initializes them. The defaults changed in JDK 24 (release note "Adjust JAXP Limits", JDK-8343004: "the default values of the limits are tuned down to more closely align with known DTDs"), so JDK 21 and JDK 25 differ:

| Property | JDK 21 default = enforced | JDK 24 and 25 default = enforced | Processors (set method) |
| --- | --- | --- | --- |
| `jdk.xml.entityExpansionLimit` | 64,000 | 2,500 | DOM, SAX, StAX, Validation, Transform (setAttribute / setProperty) |
| `jdk.xml.elementAttributeLimit` | 10,000 | 200 | same |
| `jdk.xml.maxOccurLimit` | 5,000 | 5,000 | same (schema grammars only) |
| `jdk.xml.totalEntitySizeLimit` | 5×10^7 | 100,000 | same |
| `jdk.xml.maxGeneralEntitySizeLimit` | 0 (no limit) | 100,000 | same |
| `jdk.xml.maxParameterEntitySizeLimit` | 10^6 | 15,000 | same |
| `jdk.xml.entityReplacementLimit` | 3×10^6 | 100,000 | same |
| `jdk.xml.maxElementDepth` | 0 (no limit) | 100 | same |
| `jdk.xml.maxXMLNameLimit` | 1,000 | 1,000 | same |
| `jdk.xml.xpathExprGrpLimit` / `xpathExprOpLimit` | 10 / 100 | 10 / 100 | Transform, XPath (since 19) |
| `jdk.xml.xpathTotalOpLimit` | 10,000 | 10,000 | Transform (XSLT only) |
| `jdk.xml.enableExtensionFunctions` | default true, enforced false | default false | Transform (setFeature); JDK 25 module text says the XPath API is not affected |
| `jdk.xml.overrideDefaultParser` | false | false | Transform, Validation, XPath |
| `jdk.xml.dtd.support` | absent | `allow` / `ignore` / `deny`, default `allow` (since 22) | DOM, SAX, StAX, Validation, Transform |
| `jdk.xml.jdkcatalog.resolve` | absent | `continue` / `ignore` / `strict`, default `continue` (since 22) | same |

   Per-factory setting methods (module summary "Processors" table): DOM `DocumentBuilderFactory.setAttribute` (limits) and `setFeature` (booleans); SAX `SAXParserFactory.setFeature` for features and `SAXParser.setProperty` for the limit properties; StAX `XMLInputFactory.setProperty`; Validation `SchemaFactory.setProperty` / `setFeature`; Transform `TransformerFactory.setAttribute` / `setFeature`; XPath `XPathFactory.setProperty` / `setFeature`.

2. FSP is on by default for the DOM, SAX, validation and transformation factories, but the default configuration does not restrict external connections. Only an explicit `setFeature(FSP, true)` through the API makes the JDK treat the three external access properties (`javax.xml.accessExternalDTD`, `...Schema`, `...Stylesheet`, default `all`) as denied. Even then a system property or configuration-file entry outranks that FSP-derived default, because the precedence is: API on the factory or processor, then system property, then user configuration file, then `jaxp.properties`, then defaults (FSP values). The guide states that API settings "ensure that your applications behave the same way regardless of which JDK release you're using or whether JAXP properties are set through other means". StAX does not support FSP at all; its parser observes the limits by default and takes DTD and external-entity policy from `SUPPORT_DTD`, `IS_SUPPORTING_EXTERNAL_ENTITIES`, an `XMLResolver`, and `jdk.xml.dtd.support` (22+). `jdk.xml.dtd.support` has no effect when `disallow-doctype-decl` is set on a DOM or SAX factory or `supportDTD` on a StAX factory.

3. Configuration file. JDK 21 already documents the default file `${java.home}/conf/jaxp.properties` and the user-defined file named by the system property `java.xml.config.file` (read once at JAXP initialization; a relative path is resolved against the working directory; an unreadable file is treated as absent). JDK 22 added `jdk.xml.dtd.support`, `jdk.xml.jdkcatalog.resolve` and the built-in catalog. JDK 23 added `${java.home}/conf/jaxp-strict.properties.template` (JDK-8331016, resolved 2024-05-25) with `jdk.xml.jdkcatalog.resolve=strict`, extension functions off and the smaller limits, meant to test readiness "for the upcoming change to a more secure configuration by default". JDK 24 made those limit values the defaults (JDK-8343004). The shipped JDK 25 `conf/jaxp.properties` spells them out (`jdk.xml.entityExpansionLimit=2500`, `totalEntitySizeLimit=100000`, `maxGeneralEntitySizeLimit=100000`, `maxParameterEntitySizeLimit=15000`, `entityReplacementLimit=100000`, `elementAttributeLimit=200`, `maxOccurLimit=5000`, `maxElementDepth=100`, `maxXMLNameLimit=1000`, XPath 10 / 100 / 10000, `jdk.xml.dtd.support=allow`, `jdk.xml.jdkcatalog.resolve=continue`).

4. Limit violations surface as fatal `SAXParseException`s with codes `JAXP00010001` (entity expansion), `...02` (element attributes), `...03` (max entity size), `...04` (total entity size), `...05` (max XML name), `...06` (max element depth), `...07` (entity replacement). External-access denials carry a fixed message form ("Failed to read external DTD ..., because 'http' access is not allowed due to restriction set by the accessExternalDTD property").

5. Composite processors (validator, transformer, XPath) use internal parsers for non-DOM sources; FSP set on their factories is passed to those parsers. External access properties have no effect when a resolver returns a non-null source, when a `Schema` was created explicitly with `newSchema`, or when the DTD features already prevent the external access.

## Q2. OWASP and JDK guidance per factory type; what a caller's own XMLReader, StAX reader or DOM keeps

**Answer.**

1. OWASP XXE Prevention Cheat Sheet, Java section (current text, retrieved 2026-10-27), per API:
   - `DocumentBuilderFactory`: `newDefaultInstance()`, `disallow-doctype-decl` true, FSP true, XInclude left off; `setExpandEntityReferences(false)` is not a substitute for blocking external resources.
   - `SAXParserFactory` / `XMLReader`: `newDefaultInstance()`, namespace aware, `disallow-doctype-decl` true, FSP true, parse through the configured reader. `SAXParser.parse(source, DefaultHandler)` replaces the reader's resolver with the handler, so call `reader.parse(...)` directly.
   - `XMLInputFactory` (StAX): `newDefaultFactory()`, `SUPPORT_DTD` false, `IS_SUPPORTING_EXTERNAL_ENTITIES` false, an `XMLResolver` that throws. "Disabling DTD processing does not necessarily reject the DOCTYPE declaration. StAX does not support FEATURE_SECURE_PROCESSING; use the provider's processing limits."
   - `TransformerFactory`: FSP true, `ACCESS_EXTERNAL_DTD` and `ACCESS_EXTERNAL_STYLESHEET` empty before compiling; choose the stylesheet in code; a `URIResolver` set on the factory before `newTransformer`.
   - `SchemaFactory` / `Validator`: FSP true, `ACCESS_EXTERNAL_DTD` and `ACCESS_EXTERNAL_SCHEMA` empty before `newSchema`; the restrictions also apply during validation; a resolver must be set on the factory and on each `Validator` or `ValidatorHandler`, which do not inherit it.
   - `XPath`: never the `InputSource` overloads of `evaluate`; evaluate against a document from the hardened builder.
   - JAXB `Unmarshaller`: pass a hardened StAX reader to `unmarshal`; "passing raw XML instead delegates parser configuration to the JAXB provider".
   - General: disable DTDs whenever possible and reject DOCTYPE; keep XInclude off; restrict external access for schema validation and stylesheets too; "treat an unsupported security setting as a configuration failure" and stop; pass streams, not filenames or URLs, because "external-entity controls do not restrict access to the initial resource passed directly to a parsing or processing API"; if internal DTDs are required, install a resolver that throws and set the three Xerces features false, and keep FSP plus processing limits because a resolver does not limit internal expansion. The sheet now also points to Apache Commons Secure XML as a source of preconfigured factories and lists Semgrep rules for the three parser factories.
   - OWASP XML Security Cheat Sheet: the DoS families are entity expansion (billion laughs, quadratic blowup, recursive entities), "jumbo payloads" in depth (many elements) and width (many attributes, long names and values), coercive parsing with deep unclosed nesting (stack overflow), external entity and parameter-entity retrieval, SSRF, DNS lookups through DOCTYPE system identifiers, port scanning and brute forcing through entity URLs, and schema poisoning. It gives no numeric limits; it asks for schema restrictions on lengths and occurrences and for bounded resources.

2. JDK guidance (JDK 25 guide "General Recommendations"): create a user-defined configuration file for the deployment, disable DTDs with `jdk.xml.dtd.support` when DTDs are not needed, set the limits "just large enough to accommodate the maximum amount your applications require", reduce reliance on external resources and tighten the external access properties, use a local catalog, and reject unresolved references with `jdk.xml.jdkcatalog.resolve=strict`.

3. What a caller-supplied parser keeps, from the live source and the JAXB RI 2.3.8 (the version in `pom.xml:181-182`):
   - A `SAXSource` with its own `XMLReader`: `BaseJAXBUnmarshaller.java:119-122,138-146` only installs the content handler (the boolean filter chained to the JAXB `UnmarshallerHandler`) and calls `reader.parse(input)`. Everything else is the caller's: the DTD policy (`disallow-doctype-decl`), the entity features, `load-external-dtd`, XInclude, namespace awareness, string interning, FSP and the `jdk.xml.*` limits of the factory that made the reader, the `EntityResolver`, `DTDHandler`, declaration and lexical handlers, and the `ErrorHandler`. The JAXB RI itself, when it is given a `SAXSource` with a reader, also only replaces the content and error handlers ("This will clobber such handler, if any", `UnmarshallerImpl.unmarshal0(XMLReader, ...)`). A `SAXSource` without a reader gets a reader built by the RI: `XmlFactory.createParserFactory` sets namespace awareness and FSP (unless the system property `com.sun.xml.bind.disableXmlSecurity` is true) and nothing else; it accepts DOCTYPE and internal entities within the JDK limits. xacml4j does not use that path: it builds its own `InputSource` and reader for streams, bytes, `InputSource` and `StreamSource` (`BaseJAXBUnmarshaller.java:123-141,162-213`).
   - A StAX `XMLStreamReader` or `XMLEventReader`: the reader's properties are fixed when its factory created it (`SUPPORT_DTD`, `IS_SUPPORTING_EXTERNAL_ENTITIES`, `IS_REPLACING_ENTITY_REFERENCES`, `RESOLVER`, the `jdk.xml.*` limits, or Woodstox's `com.ctc.wstx.*` limits). xacml4j wraps it in a delegate (`BooleanStreamReader`, `BooleanEventReader`, lines 243-319) and the JAXB RI bridges it with `StAXStreamConnector` without creating a parser. A delegate can observe events (including `XMLStreamConstants.DTD` and `ENTITY_REFERENCE`) and count, but cannot change the underlying parser.
   - A DOM `Node` or `DOMSource`: parsing already happened in the caller's builder with the caller's DTD and entity policy; the RI's `DOMScanner` walks the tree without a parser (`UnmarshallerImpl.unmarshal0(Node, ...)`). A `Document` whose source had a DOCTYPE carries a `DocumentType` node (`Document.getDoctype()`), and a builder with `setExpandEntityReferences(false)` leaves `EntityReference` nodes in the tree. There are no bytes to count, so only structural limits (depth, element count, attributes, text and attribute lengths, names) can be enforced by walking the tree.
   - Inside the RI, `Content` and other `xs:any` payloads become DOM through a `TransformerFactory` that the RI creates with FSP (`XmlFactory.createTransformerFactory`); the events come from xacml4j's reader, so no new input source is opened, but this factory is outside any xacml4j owner and is switched off by `com.sun.xml.bind.disableXmlSecurity`.
   - Xerces-specific: the `StreamSource` branch (`BaseJAXBUnmarshaller.java:129-134`) builds `new InputSource(stream.getSystemId())`; when the source carries no byte or character stream the parser opens the system identifier (file or URL). That is the "initial resource" case OWASP warns about and is not covered by any entity restriction.

## Judgement of D6 and of the parse-security attack corpus

**D6 is sound in its structure (one owner, FSP, DOCTYPE rejection, explicit external access denial, fail-closed setup, a limits filter on every path) and needs six corrections.**

1. The JDK limit defaults are a moving target and the API must pin them. On JDK 25 the parser already enforces depth 100 and 200 attributes per element by default; D6 proposes 256 and 256. Unless `SecureXml` sets `jdk.xml.maxElementDepth` and `jdk.xml.elementAttributeLimit` explicitly, a 150-deep policy fails with the JDK's `JAXP00010006` message instead of the `LIM4nn` diagnostic, and the same policy parses on JDK 21. Conversely, a deployment `java.xml.config.file` or `-Djavax.xml.accessExternalDTD=all` would re-open external access that D6 believes FSP closed. Explicit API settings have the highest precedence and are the only way to be JDK- and deployment-independent (Q1 item 2).
2. DOCTYPE rejection needs a mechanism per path: `disallow-doctype-decl` on SAX and DOM factories; `SUPPORT_DTD=false` plus a delegate that fails on a `DTD` event for StAX; `Document.getDoctype() != null` for DOM input; the lexical handler property on a caller's `XMLReader` where the reader accepts it; `jdk.xml.dtd.support=deny` on the validation and transformer factories (JDK 22+). Keep the entity features and the throwing resolvers as the second layer, as OWASP and the JDK guide both advise.
3. The proposed byte and count limits are too loose for a default and inconsistent with the spec's own heap bound ("without heap growth over 64 MB", `specs/parse-security/spec.md:20`): a legitimate 64 MiB document or 2,000,000 elements expand to several hundred MB of JAXB and DOM objects. The corpora are tiny by comparison (table below).
4. Two bounds are missing: a total-characters limit (the only size bound on caller-supplied DOM and StAX input, where no bytes exist; Woodstox has `P_MAX_CHARACTERS` for the same reason), and the treatment of namespace declarations, which SAX does not report as attributes in namespace-aware mode but which cost memory like attributes.
5. "One owner" cannot cover the JAXB RI's internal `TransformerFactory` (Q2 item 3) nor a caller's parser. The design should say so and add the two cheap guards: fail fast when `com.sun.xml.bind.disableXmlSecurity` is true, and run the suite once under the strict template to prove that no un-owned factory depends on the JDK defaults.
6. Sources that are only a system identifier (`StreamSource` or `InputSource` without a stream) must be rejected or resolved by `SecureXml` under an explicit option; today the parser opens them (`BaseJAXBUnmarshaller.java:129-134`).

**Attack corpus judgement.** The scenarios in `specs/parse-security/spec.md` cover file and http external entities through every byte-based entry point, billion laughs and quadratic blowup, factory setup failure, transformer settings, depth, caller-reader element counts, the strict option, JSON limits and duplicates, and schema resolution. Missing cases, each cheap to add:

1. External DTD by system identifier without any entity (`<!DOCTYPE a SYSTEM "http://127.0.0.1:port/a.dtd">`) and the DNS-only variant with a `PUBLIC` identifier: proves DOCTYPE rejection fires before any resolution.
2. Parameter-entity out-of-band exfiltration (`<!ENTITY % dtd SYSTEM "http://...">%dtd;`), the classic blind XXE.
3. XInclude inside `Content` (`xi:include href="file:///..."`) and inside `AttributeValue`.
4. `xsi:schemaLocation` pointing at the recording server, parsed with validation off and on (D7): no request in either case.
5. `StreamSource` and `InputSource` carrying only a `file:` or `http:` system identifier, for every unmarshaller: no file read, no request, a security diagnostic.
6. Caller-supplied parsers with DTDs allowed: a `SAXSource` reader without `disallow-doctype-decl`, a JDK `XMLStreamReader` with `SUPPORT_DTD` true and one with false, an `XMLEventReader`, and a DOM parsed by a lenient builder (with a `DocumentType` node, and with an `EntityReference` node). Expected: the DOCTYPE diagnostic in strict mode; documented behaviour in default mode.
7. Request-supplied XPath in a `multiple:content-selector` attribute with more than 10 groups and more than 100 operators, and a deeply nested `Content` document: proves the FSP XPath limits and the depth limit protect the multiple-decision handler.
8. Width attacks: 201 attributes on one element, 201 namespace declarations on one element, an attribute value of 1 MiB + 1, a text node of 8 MiB + 1, a 1,001-character element name and namespace URI, and a document just over 16 MiB in UTF-8 and the same text in UTF-16 (byte versus character accounting).
9. Total-characters attack through a caller DOM: many elements each holding a 1 MiB text node, under the element limit but over the total-characters limit.
10. JSON: nesting 256 and 10,000 deep (stack safety), a 1,001-digit number, a string over 8 MiB, a document over 16 MiB, duplicate members at the top level and inside `Attribute`, and the leniency cases Gson's `LEGACY_STRICT` still accepts (unescaped control characters, `\'`): the provider must run in `Strictness.STRICT` (D8 criterion).
11. A positive control per limit at exactly the limit, so the filter is off by one in neither direction, and a run of the whole suite under `-Djava.xml.config.file=<copy of jaxp-strict.properties.template>` with `jdk.xml.dtd.support=deny` added, to show that no factory outside `SecureXml` relies on JDK defaults.

## Recommendations for the design decisions, most important first

1. **D6, pin every JDK limit and external-access property through the API.** `SecureXml` sets, on each factory or parser it creates: FSP true; `disallow-doctype-decl` true (SAX, DOM) or `SUPPORT_DTD` false plus `IS_SUPPORTING_EXTERNAL_ENTITIES` false (StAX); the three Xerces entity features false; `setXIncludeAware(false)`; `ACCESS_EXTERNAL_DTD`, `ACCESS_EXTERNAL_SCHEMA`, `ACCESS_EXTERNAL_STYLESHEET` empty; `jdk.xml.maxElementDepth`, `elementAttributeLimit`, `maxXMLNameLimit` from `ParseOptions`; the entity limits at the JDK 24 strict values; `jdk.xml.dtd.support=deny` and `jdk.xml.jdkcatalog.resolve=strict` when the runtime is JDK 22 or later (these two may be the only properties whose absence is tolerated, and only on JDK 21). Reason: Q1 items 2 and 3; the JDK 25 guide line "By setting JAXP properties through JAXP factories, you can ensure that your applications behave the same way regardless of which JDK release you're using or whether JAXP properties are set through other means".
2. **D6 and D2, translate JDK limit errors into `LIM4nn` diagnostics.** Match `JAXP00010001` to `JAXP00010007` in the `SAXParseException` message and the external-access denial message form; take line and column from the exception. The filter counts what the JDK does not (bytes, element count, attribute value length, text length, total characters) and everything on caller-supplied paths.
3. **D6, DOCTYPE rejection per path** as listed in judgement item 2; keep the second layer (features false, throwing `EntityResolver`, declaration and lexical handlers) that `BaseJAXBUnmarshaller.java:174-211` already has; add `Document.getDoctype()` and `DTD`-event checks; use `Document.getDoctype()` also in `DOMUtil.copyNode` callers for `Content` nodes that arrive as DOM.
4. **D6, adopt the proposed defaults table** (document 16 MiB, depth 100, elements 500,000, attributes 200, attribute value 1 MiB, text 8 MiB, name 1,000, total characters 16 Mi, JSON 255 / 8 MiB / 1,000 / 1,000 / 16 MiB), and add the total-characters and namespace-declaration rules. Record the corpus statistics above as the sizing evidence.
5. **D6 and spec "Caller-supplied parsers", define the contract.** State what the caller keeps (Q2 item 3). In default mode the limits filter counts and rejects DOCTYPE where it can observe it (DOM `DocumentType`, StAX `DTD` event, lexical handler on a SAX reader that accepts the property); in strict mode caller parsers are rejected outright (already in the spec). Add the UNVERIFIED items to `ParseLimitsTest`: whether the JDK StAX reader emits a `DTD` event with `SUPPORT_DTD` false, and whether JAXB's `DOMScanner` descends into `EntityReference` nodes.
6. **D6, reject system-identifier-only sources.** In `BaseJAXBUnmarshaller` (and in `DOMUtil.parseXml(InputSource)`), fail with a security diagnostic when a `StreamSource` or `InputSource` has neither a byte nor a character stream, unless a `ParseOptions` flag allows `SecureXml` to open the identifier itself with the external-access rules applied. OWASP: "external-entity controls do not restrict access to the initial resource passed directly to a parsing or processing API".
7. **D6, pin the implementation and configure once.** Create the JDK factories with `newDefaultInstance()` / `newDefaultFactory()` (OWASP), or with the explicit Woodstox factory class if D9 adopts Woodstox, never through the lookup mechanism (a classpath provider would silently change the security model). Configure each factory once per JVM and create a parser per use (D9 already plans a `SAXParser` per thread). Drop `allow-java-encodings` (`DOMUtil.java:110`), a non-standard extension that no fixture needs. Fail-closed setup as D6 says, replacing the log-and-continue block at `DOMUtil.java:112-114` and the unhardened `TransformerFactory` at line 86.
8. **D6 and D9, Woodstox path.** If the direct StAX parser lands on Woodstox, map the `ParseOptions` limits to Woodstox's native properties (`P_MAX_ELEMENT_DEPTH`, `P_MAX_ELEMENT_COUNT`, `P_MAX_ATTRIBUTES_PER_ELEMENT`, `P_MAX_ATTRIBUTE_SIZE`, `P_MAX_TEXT_LENGTH`, `P_MAX_CHARACTERS`, `P_MAX_CHILDREN_PER_ELEMENT`, `P_MAX_ENTITY_COUNT`, `P_MAX_ENTITY_DEPTH`, `P_MAX_DTD_DEPTH`) and keep the delegate only for caller readers; measure both with the JMH pair. Note Woodstox 7.3.0's `P_MSV_SCHEMA_EXTERNAL_ACCESS` (default false) if its schema factories are ever used.
9. **D7, resolvers and schemas.** Set the `LSResourceResolver` and the two external-access properties on the `SchemaFactory` before `newSchema(Source...)` and on every `Validator` and `ValidatorHandler` (not inherited, OWASP). Because an explicit `Schema` bypasses the external-access properties (JDK guide), the resolver must reject anything outside the class path, and the "No external schema access" scenario should also use the recording HTTP server. `jdk.xml.maxOccurLimit` needs no change (no numeric `maxOccurs` in the vendored schemas). Note the 2,853 fixtures with `xsi:schemaLocation` hints: with a compiled `Schema` the hints are not fetched, which the scenario should assert.
10. **D6, JAXB-internal factories.** Fail fast in `JAXBUtils` when `com.sun.xml.bind.disableXmlSecurity` is true, and document that the RI's internal `TransformerFactory` (the DOM builder for `Content`) is FSP-hardened by the RI but not owned by `SecureXml`. Add the strict-template CI run (corpus item 11) as the proof that no un-owned factory depends on JDK defaults.
11. **D8, JSON.** Both candidates meet the limits: Jackson through `StreamReadConstraints` (depth 1,000, string 20,000,000, number 1,000, name 50,000 by default; document length and token count unlimited) plus `STRICT_DUPLICATE_DETECTION`; Gson 2.15 through `JsonReader.setNestingLimit` (default 255) and `Strictness.STRICT` plus a hand-written duplicate check. Add "runs in strict mode (RFC 8259 only)" to the D8 criteria.
12. **Design "Non-Goals".** Keep XPath cost limits for `AttributeSelector` out of scope, but add one sentence that request-supplied `multiple:content-selector` XPath is evaluated during request handling under the FSP XPath limits of `XPathProvider`, and that the corpus proves it (item 7).
13. **Docs (TESTING.md or the module README).** State that `SecureXml`'s API settings override `java.xml.config.file` and `jaxp.properties`, so operators change limits through `ParseOptions`, not the JDK file; and that Apache Commons Secure XML 1.1.0 exists as an alternative factory owner should the maintainer prefer a dependency (its threat model and limit coverage were not read here, UNVERIFIED).

## Risks and open questions

- UNVERIFIED: whether the JDK StAX reader reports a `DTD` event when `SUPPORT_DTD` is false (OWASP says the DOCTYPE is not necessarily rejected). Decides how DOCTYPE rejection works on caller StAX readers; test both JDK StAX and Woodstox.
- UNVERIFIED: whether the JAXB RI `DOMScanner` descends into `EntityReference` nodes of a caller DOM; decides whether the DOM walk must reject such nodes.
- UNVERIFIED: whether `Validator.setProperty` accepts the `jdk.xml.*` limits; set them on the `SchemaFactory` (documented) and attempt them on each `Validator`, tolerating `SAXNotRecognizedException` only there.
- The element-count and byte defaults rest on an estimate of 200 to 500 B per element in JAXB and DOM; `ParseLimitsTest` should measure a 500,000-element document with `-Xmx` to confirm the heap bound before the defaults are frozen.
- The JDK docs disagree with themselves on `xpathTotalOpLimit` (10,000 versus 100,000) and on whether `enableExtensionFunctions` covers the XPath API; neither matters to xacml4j, but the design should cite the module summary, not the guide, for numbers.
- The JAXB RI 4.x (Jakarta) line was not read; if `upgrade-dependencies` migrates, re-check `XmlFactory` and `UnmarshallerImpl` there.
- Woodstox limit defaults are not in the constants file read here; if adopted, read `ReaderConfig` for the defaults before relying on them.
- A deployment that must accept internal DTD subsets has no path after D6 (the proposal marks this BREAKING and offers no switch); the strict-template CI run and the release note are the mitigations.
- JDK 21 is no longer the project baseline (JDK 25), but downstream users of `xacml-core` on JDK 21 would get JDK 21 defaults for anything `SecureXml` does not set; recommendation 1 closes that gap.
