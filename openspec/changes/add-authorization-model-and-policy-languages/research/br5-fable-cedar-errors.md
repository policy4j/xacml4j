## 1. Facts

**1.1 Cedar's authorization semantics for errors (fetched, Lean model on `main`).**

- `Cedar/Spec/Authorizer.lean` (https://raw.githubusercontent.com/cedar-policy/cedar-spec/main/cedar-lean/Cedar/Spec/Authorizer.lean): `satisfied policy req entities := (evaluate policy.toExpr req entities) = .ok true`; `hasError` is true when `evaluate` returns `.error _`; `errorPolicies` collects the ids of erroring policies regardless of effect; `isAuthorized` computes `forbids := satisfiedPolicies .forbid`, `permits := satisfiedPolicies .permit`, `erroringPolicies := errorPolicies`, and returns `{ decision := .allow, determiningPolicies := permits, erroringPolicies }` when `forbids.isEmpty && !permits.isEmpty`, else `{ decision := .deny, determiningPolicies := forbids, erroringPolicies }`. An erroring policy is therefore never satisfied; it contributes only to `erroringPolicies`.
- `Cedar/Spec/Response.lean` (same base URL): `Decision` is `allow | deny`; `Response` has `decision`, `determiningPolicies : Set PolicyID`, `erroringPolicies : Set PolicyID`. There is no third decision value.
- `Cedar/Spec/Value.lean`: `inductive Error | entityDoesNotExist | attrDoesNotExist | tagDoesNotExist | typeError | arithBoundsError | extensionError`; `Result α := Except Error α`. These six are the only evaluation errors in the model.
- Production engine (https://raw.githubusercontent.com/cedar-policy/cedar/main/cedar-policy-core/src/authorizer.rs): `enum ErrorHandling { Skip }` with the doc comment "We currently only have one mode: `ErrorHandling::Skip`. Other modes were debated during development, so this is here as an easy way to add modes if the future if we so decide"; on `Err(e)` the authorizer pushes `AuthorizationError::PolicyEvaluationError { id, error }` and, under `Skip`, treats the policy as unsatisfied (`ErrorState::Error`). Its unit test `skip_on_error_tests` asserts: `permit(all)` plus `permit ... when { context.bad == 2 }` plus `forbid ... when { context.bad == 2 }` (both error on an empty context) is `Allow`; adding `forbid(principal, action, resource)` makes it `Deny`.
- Reference guide (https://docs.cedarpolicy.com/auth/authorization.html, source https://raw.githubusercontent.com/cedar-policy/cedar-docs/main/docs/collections/_auth/authorization.md): each policy evaluates to `true`, `false` or `error`; rules: any satisfied `forbid` gives Deny, else any satisfied `permit` gives Allow, else Deny; diagnostics hold the determining policies "along with the particulars of the errors"; the three stated properties are "default deny", "forbid overrides permit" and "skip on error: if a policy's evaluation returns `error`, the policy does not factor into the authorization response; it is skipped". Scope constraints "cannot possibly evaluate to `error`"; conditions evaluate in order and an error stops the policy.
- What the response reports: Rust `Diagnostics::reason()` (policies that contributed) and `Diagnostics::errors()` ("should be treated as unordered, since policies may be evaluated in any order"), https://docs.rs/cedar-policy/latest/cedar_policy/struct.Diagnostics.html (4.14.0, 2026-10-17); cedar-java `AuthorizationSuccessResponse` has `Decision { Allow, Deny }` and `Diagnostics { reason: Set<String>, errors: List<AuthorizationError{policyId, DetailedError}> }`, while `AuthorizationResponse` is `Success` or `Failure` (failure is for requests that cannot be processed at all, with `errors` and `warnings`) (https://raw.githubusercontent.com/cedar-policy/cedar-java/main/CedarJava/src/main/java/com/cedarpolicy/model/AuthorizationSuccessResponse.java and `.../AuthorizationResponse.java`); Amazon Verified Permissions `IsAuthorized` returns `decision` ALLOW|DENY, `determiningPolicies` and `errors` ("for example, a policy references an Entity or entity Attribute that does not exist in the slice") (https://docs.aws.amazon.com/verifiedpermissions/latest/apireference/API_IsAuthorized.html); the shared corpus https://github.com/cedar-policy/cedar-integration-tests (README, Apache-2.0) expects per request `decision`, `reason` and `errors` ("Expected policies that resulted in errors"), is generated by a six-hour fuzzing run plus handwritten tests, and gates CI for `cedar` and `cedar-java`.

**1.2 The authors' rationale (fetched).**

- Reference guide (URL above): "An alternative authorization algorithm we considered would be to `Deny` a request when any policy evaluation exhibits an error ... deny-on-error raises concerns of safety. An application that was working fine with 100 policies might suddenly start denying all requests if the 101st policy has an error. Skip-on-error avoids this dramatic failure mode, and is more flexible: applications can always choose to look at the authorization response's diagnostics and take a different decision if an evaluated policy produces errors."
- Designer's blog, "Why does Cedar ignore policies that error?" (https://cedarland.blog/design/why-ignore-errors/content.html, undated page linked from the guide): errors exist instead of a nil value because `!(principal.jobRole == "external_contractor")` with a nil `jobRole` "would surprisingly permit access"; "only the policy author can resolve the ambiguity"; on forbids: "One of the larger debates during Cedar's design was whether errors in forbid statements should result in a policy being skipped ... this has to be weighed against the blast impact of a mistake in a single policy resulting in 100% of all authorization queries returning a Deny decision ... In the end, this was a debate with no winning side ... Cedar behaves consistently"; mitigations named: validation before deployment, shadow testing, and diagnostics so that "system owners may use these diagnostics to observe when an error occurred in a forbid statement and can elect to treat that as a fail-closed scenario".
- OOPSLA 2024 paper, arXiv:2403.04651 (v2, 2024-03-08), via the arXiv LaTeX source: §3.3 gives `authorize(μ, C, σ)` where `evaluate(e)` is a partial function and `C_S` holds the policies whose expression "evaluates to true", so a stuck (erroring) policy is simply not in `C_S`; a footnote adds that the implementation also reports "any policies that exhibited errors when evaluated"; §3.2: "Stuck states in the semantics correspond to raised errors in the implementation ... evaluation will get stuck on a projection `E::\"s\".f` when `E::\"s\"` does not exist ... We considered creating a null value, but decided to avoid repeating that 'billion dollar mistake'"; `==` on non-existent references succeeds; §2.4 lists safety as default deny, forbid overrides permit, and determinism; §3.5 lists the proved properties: forbid trumps permit, default deny, explicit allow, sound slicing, validation soundness. The paper does not argue skip-on-error itself; the argument lives in the guide and the blog.

**1.3 Errors that remain possible after schema validation (fetched).**

- Validation page (https://docs.cedarpolicy.com/policies/validation.html): validation soundness leaves three error classes: "Errors due to integer overflow" (`arithBoundsError`), "Errors due to missing entities" (an entity literal or a principal, resource or attribute entity "that does not exist in the entities used to evaluate the policy"; "Request validation (RFC 11) and schema-based JSON parsing do not confirm the existence of entities"), and extension constructors on non-literal strings in non-strict mode (`extensionError`). Everything else "will never happen" for requests and entities that conform to the schema; non-conforming data yields `attrDoesNotExist` or `typeError` at run time (the page's `Employee::"Rick"` example).
- Datetime extension (https://cedar-policy.github.io/rfcs/0080-datetime-extension.html, stabilised in 4.4.0): `datetime`, `duration`, `.offset()` and `.durationSince()` error on malformed input or 64-bit overflow. Data types page (https://docs.cedarpolicy.com/policies/syntax-datatypes.html): "A policy that results in an error is ignored, meaning that a Permit policy might unexpectedly fail to allow access, or a Forbid policy might unexpectedly fail to block access." Tags: `getTag` on an absent tag errors, but the validator's capability tracking prevents it in validated policies (https://cedar-policy.github.io/rfcs/0082-entity-tags.html). Level validation, RFC 76, bounds entity dereferencing so that a correctly sliced entity store cannot produce missing-entity errors (CHANGELOG 4.4.0; `Cedar/Thm/Validation/Levels.lean` per the cedar-lean README).

**1.4 Proved properties and their dependence on skip-on-error (fetched `Cedar/Thm/Authorization.lean`; dependence analysis is inference).**

| Theorem (file `cedar-lean/Cedar/Thm/Authorization.lean`) | Statement | Holds under deny-on-error? | Holds under forbid-only fail-closed? |
| --- | --- | --- | --- |
| `forbid_trumps_permit` | a satisfied forbid gives deny | yes | yes |
| `allowed_only_if_explicitly_permitted` / `default_deny` | allow needs a satisfied permit | yes | yes |
| `allowed_iff_explicitly_permitted_and_not_denied` | allow iff some permit satisfied and no forbid satisfied | no (an erroring policy would deny) | no, the "if" direction fails when a forbid errors |
| `denied_iff_explicitly_denied_or_not_permitted` | deny iff a forbid is satisfied or no permit is | no | no |
| `order_and_dup_independent` | result independent of policy order and duplicates | yes | yes |
| `unchanged_allow_when_add_permit` | adding a permit cannot turn Allow into Deny | no (an erroring permit would) | yes |
| `unchanged_deny_when_add_forbid` | adding a forbid cannot turn Deny into Allow | yes | yes |
| `determiningPolicies_of`, `unchanged_erroring_when_add_policy`, `determining_erroring_disjoint_when_unique_ids` | determining set is exactly the satisfied permits or forbids; erroring set only grows; determining and erroring are disjoint | definitions change | holds if erroring forbids stay in `erroringPolicies` and are not counted as determining |

All theorems are stated over `satisfied`, which is defined as `evaluate = .ok true`, so skip-on-error is built into the definitions rather than assumed by a hypothesis. Sound slicing (`Cedar/Thm/Authorization/PolicySlice.lean`, imported by the file above) and the symbolic compiler encode the same `isAuthorized`; a fail-closed variant would need its own encoding, which is why xacml4j cannot borrow the Lean proofs or the SMT analysis for anything but Cedar-exact semantics.

**1.5 What an erroring forbid leads to (fetched facts, summarised).** With a satisfied permit present, Allow: the Lean definitions ignore it, the Rust test above asserts it, the data types page warns that "a Forbid policy might unexpectedly fail to block access", and the blog calls it the debate "with no winning side". Without a satisfied permit the result is Deny by default deny, so the exposure is exactly the set of requests that some permit grants and a broken forbid was meant to exclude.

**1.6 XACML 3.0 Indeterminate semantics (fetched from http://docs.oasis-open.org/xacml/3.0/errata01/os/xacml-3.0-core-spec-errata01-os-complete.html, OASIS Standard incorporating Approved Errata, 12 July 2017).**

- §5.53: "Indeterminate: the PDP is unable to evaluate the requested access. Reasons for such inability include: missing attributes, network errors while retrieving policies, division by zero during policy evaluation, syntax errors ...". §7.4: Indeterminate "is said to be the result of an invalid expression, or an operational error occurring during the evaluation of the expression".
- §7.3.5 and §7.19.3: a missing attribute with `MustBePresent="true"` is Indeterminate with status `missing-attribute`; the `<Status>` MAY list the missing attributes (§5.58 `MissingAttributeDetail`); "A PEP MAY resubmit a refined request context ... by adding attribute values for the attribute names that were listed"; the PDP "MUST NOT list the names and data-types of any attribute for which values were supplied", which "forces the PDP to eventually return ... Permit, Deny, or Indeterminate with some other status code". §7.19.1 and §7.19.2: unsupported elements or functions, syntax and static type errors are Indeterminate with `syntax-error` or `processing-error`. §7.15: unresolvable policy references are Indeterminate. §7.18: an Indeterminate obligation or advice expression makes the whole rule or policy Indeterminate.
- §7.10: extended Indeterminate values {D}, {P}, {DP} carry "the potential effect values which could have occurred"; "The final decision returned by a PDP cannot be an extended Indeterminate", it is returned as plain Indeterminate. §7.11 rule table: an Indeterminate target or condition gives Indeterminate{P} for Effect Permit and Indeterminate{D} for Effect Deny. §7.12 to §7.14: policies and policy sets delegate to the combining algorithm; an Indeterminate target maps Permit to Indeterminate{P}, Deny to Indeterminate{D}, Indeterminate to Indeterminate{DP}. §7.17: "If the PDP cannot make a decision, then an Indeterminate `<Decision>` element SHALL be returned."
- Appendix C (normative pseudo-code): C.2 deny-overrides: Deny if any Deny; else Indeterminate{DP} if any {DP}, or if any {D} together with a {P} or a Permit; else Indeterminate{D}; else Permit; else Indeterminate{P}; else NotApplicable. C.4 permit-overrides is the mirror image. C.6 deny-unless-permit: Permit if any Permit, otherwise Deny ("an Indeterminate or NotApplicable must never be the result"); C.7 permit-unless-deny: Deny if any Deny, otherwise Permit. C.8 first-applicable: on an error "the evaluation SHALL halt, and the policy shall evaluate to Indeterminate". C.9 only-one-applicable: errors give Indeterminate. C.10 legacy 1.0 deny-overrides: at rule level a potential Deny error gives Indeterminate; at policy level "if any policy evaluates to Indeterminate, the result is Deny", the only fail-closed-to-Deny rule in the standard (conformance case IID008 is titled "Another Deny (can't return Indeterminate)", `xacml-conformance-tests/src/test/resources/xacml3.0-ct-v.0.4/ConformanceTests.html:1446`).
- §5.54 to §5.57 Status: `StatusCode` (major value plus optional minor codes), `StatusMessage`, `StatusDetail` (arbitrary XML, but "A PDP MUST NOT return a `<StatusDetail>` element in conjunction with the `ok`", `syntax-error` or `processing-error` status values; with `missing-attribute` it MAY carry `MissingAttributeDetail`). §5.48: `PolicyIdentifierList` lists "all policies which were found to be fully applicable, whether or not the `<Effect>` ... was the same or different from the `<Decision>`"; a NotApplicable decision "MUST return an empty list".
- PEP bias, §7.2: base PEP behaviour for NotApplicable and Indeterminate "is undefined"; deny-biased PEP: Permit permits, "All other decisions SHALL result in the denial of access", and "other actions, e.g. consultation of additional PDPs, reformulation/resubmission of the decision request, etc., are not prohibited"; permit-biased is the mirror. §9.1.6: "a PEP must deny access unless it receives an explicit Permit"; §9.1.7 warns that negative rules "can lead to policy violations ... when attributes are suppressed", the XACML statement of the erroring-forbid hazard.
- What PEP designers expect today: the OpenID AuthZEN issue "Support for Indeterminate Decision / Evaluation Status in Authorization Responses" (https://github.com/openid/authzen/issues/456, opened 2026-03-19) asks for a signal distinct from deny because "PEPs may need to react differently: Deny → block request; Indeterminate → retry, fallback, step-up auth, or degrade access", citing XACML's four-valued decision as the model.

## 2. Options, with decisions on example policy sets

Example data (inference): request principal `User::"alice"`, action `Action::"view"` (S4 uses `Action::"delete"`), resource `Doc::"d1"` with attribute `owner` only, empty context. Policies: P1 `permit(principal == User::"alice", action, resource);`; Pe `permit(principal, action, resource) when { resource.tag == "public" };` (errors: `attrDoesNotExist`); Fe `forbid(principal, action, resource) when { resource.tag == "secret" };` (errors); F1 `forbid(principal, action == Action::"delete", resource);`. Sets: S1 = {Pe} (an erroring permit); S2 = {P1, Fe} (an erroring forbid next to a matching permit); S3 = {Pe, Fe} (only erroring policies); S4 = {Pe, F1} on a delete request; S5 = {Fe}.

Definitions of the options as xacml4j rule-combining algorithms over the compiled rules (one compiled `Rule` per Cedar policy; any Indeterminate{P} or {D} from a rule counts as "the Cedar policy errored", whatever its cause: missing attribute, type error, PIP failure):

- A, Cedar exact: Deny if any forbid rule is Permit-satisfied... precisely: Deny if any forbid is satisfied; else Permit if any permit is satisfied; else NotApplicable; erroring rules are skipped and their ids and statuses are collected as diagnostics. A Cedar facade (`CedarAuthorizer`) maps NotApplicable to Cedar Deny with an empty determining set, so the Cedar API returns exactly the Lean `Response`. Inside an XACML policy set the value NotApplicable is used so that the Cedar policy set composes like any other policy (a hard Deny would override every sibling under deny-overrides).
- B, XACML native: the compiled rules under standard `deny-overrides` (C.2); errors propagate as Indeterminate{P}, {D}, {DP}; NotApplicable is mapped to Deny by the Cedar facade; the top-level PDP result is Indeterminate with the recorded status.
- C, configurable: the compiler emits one of the algorithm ids below per policy set (an explicit option, or an annotation on the Cedar policy set file), with a PDP-wide default.
- D, hybrid "forbid fail-closed": erroring permits are skipped as in A; an erroring forbid makes the policy set Indeterminate{D} (variant D1, surfaced to XACML) or Deny (variant D2, Cedar-shaped); satisfied forbids still give Deny and satisfied permits Permit.

Decision table (Cedar column from the Lean definitions in 1.1; the "PEP" row assumes a deny-biased PEP, §7.2.2):

| Set | Cedar (Lean) | A | B (deny-overrides) | D1 | D2 |
| --- | --- | --- | --- | --- | --- |
| S1 {Pe} | Deny, determining {}, errors {Pe} | NotApplicable (facade: Deny), errors {Pe} | Indeterminate{P} → Indeterminate | NotApplicable (facade: Deny) | NotApplicable (facade: Deny) |
| S2 {P1, Fe} | Allow, determining {P1}, errors {Fe} | Permit, errors {Fe} | Permit + Indeterminate{D} → Indeterminate{DP} → Indeterminate | Indeterminate{D} → Indeterminate | Deny |
| S3 {Pe, Fe} | Deny, determining {}, errors {Pe, Fe} | NotApplicable (facade: Deny) | Indeterminate{DP} → Indeterminate | Indeterminate{D} → Indeterminate | Deny |
| S4 {Pe, F1}, delete | Deny, determining {F1}, errors {Pe} | Deny | Deny | Deny | Deny |
| S5 {Fe} | Deny, determining {}, errors {Fe} | NotApplicable (facade: Deny) | Indeterminate{D} → Indeterminate | Indeterminate{D} → Indeterminate | Deny |
| PEP outcome (deny-biased) | Allow only in S2 | access only in S2 | no access in any set | no access in any set | no access in any set |

For reference, the other standard algorithms do not reproduce Cedar even without errors: deny-unless-permit (C.6) ignores a satisfied forbid when a permit is satisfied, and permit-unless-deny (C.7) permits when nothing applies.

Effects of each option (inference from the facts above):

- Differential testing. A: decisions, determining sets and erroring sets match cedar-java (`AuthorizationSuccessResponse.getReason()`, `getErrors()`), the Lean CLI (`cedar-lean-cli evaluate authorize`, which prints the `Response` record) and the integration corpus fields `decision`, `reason`, `errors` one to one; the facade mapping NotApplicable to Deny is the only translation. D: the oracle must be post-processed: whenever `errors` contains a forbid id and the corpus expects Allow, the expected result becomes Deny (D2) or Indeterminate (D1); the corpus still provides the erroring sets. B: every test with a non-empty `errors` list mismatches in decision shape and loses the determining semantics; only error-free tests remain usable, and the fuzzed corpus is built to exercise errors (proportion UNVERIFIED).
- Mixing Cedar and XACML policies in one PDP. A and D2 compose as Permit, Deny or NotApplicable children; B and D1 compose through the extended Indeterminate rules of C.1, so XACML parents see the error and deny-overrides escalates it. In all variants the compiled rules already record per-rule statuses, but the global status keeps only the first error (`RootEvaluationContext.java:203-209`), so a skipped Cedar error can leak into the status of an unrelated later Indeterminate result; the Cedar algorithm must keep its diagnostics in its own structure and must not set the global status for Permit, Deny or NotApplicable results (today `Rule.evaluate` sets it before the algorithm runs, `Rule.java:120,137,146`), which needs a small additive context API to scope or clear statuses.
- Security. A is fail-open with respect to a broken guardrail (S2) and fail-closed everywhere else; the exposure is bounded by default deny and visible in diagnostics. B, D1 and D2 are fail-closed for forbid errors; B is also fail-closed for permit errors, which only reduces availability (S1 is denied either way). In xacml4j's architecture transient PIP failures are more likely than in Cedar's entity-store model, because attributes are fetched during evaluation (`PolicyInformationPoint.java:52-66`); under A an unavailable attribute source silently disables every Cedar forbid that reads it, which is the §9.1.7 "attributes are suppressed" hazard at scale.
- XACML conformance suites. All four options live under new algorithm ids, and the suites only use standard ids, so none of them can change a conformance result; the 66 Indeterminate expectations (1.7) and the opt-in requirement (`spec.md:3-12`) guard against the only dangerous design, a PDP-wide error mode that reaches `Rule`, `Condition` or the standard algorithms.
- PEP contract. A and D2 answer like Cedar (Permit, Deny, NotApplicable with `ok` status); the XACML Result cannot carry `StatusDetail` with `ok` (§5.57), so Cedar diagnostics need another channel (2.1 below). B and D1 answer like XACML (Indeterminate with `missing-attribute` or `processing-error`), which keeps the §7.19.3 resubmission protocol and the AuthZEN-style "retry, fallback, step-up" reaction available to the PEP.

**2.1 Diagnostics channel (inference).** Cedar diagnostics (determining and erroring policy ids with their errors) fit in: (a) a typed attachment on the Java `Result` (additive getter; the facade and audit use it); (b) an advice `urn:xacml4j:names:cedar:1.0:advice:diagnostics` with attribute assignments, which XACML allows for Permit and Deny only (§7.18, `RootEvaluationContext.java:274-306`), so S1, S3 and S5 under A would lose it in the XML response; (c) a minor `StatusCode` under `ok` plus a `StatusMessage` (allowed by §5.55 and §5.56; `StatusDetail` is not); (d) PDP metrics (`DefaultPolicyDecisionPoint.java:174-184` already counts decisions). (a) plus (d) always, (b) for Permit and Deny, (c) optional, is the combination that keeps XML and JSON responses standard.

## 3. Recommendation, risks, breaking changes, open questions

**Recommendation.** Implement C with A as the default and D1 as the only alternative; do not implement B. Concretely: one algorithm `urn:xacml4j:names:cedar:1.0:rule-combining-algorithm:cedar` (A) and one `...:cedar-forbid-fail-closed` (D1), selected per compiled policy set by a compiler option with a PDP-wide default of A; diagnostics as in 2.1; a metric and a log line per erroring Cedar policy; and the schema-based validation of the authorization-model work as the first line of defence, because validated policies can only fail on overflow, missing entities and non-literal extension arguments (1.3).

Why A as the default: the Cedar front end's promise is Cedar semantics, and Cedar's semantics are the Lean definitions, the Rust engine, cedar-java, Verified Permissions and the shared corpus, all of which skip erroring policies and report them; A is the only option whose correctness can be established by differential testing against those oracles, and the Lean properties of 1.4 transfer to it unchanged. Cedar's own designers chose availability over fail-closed forbids after debating exactly this point, and they point to diagnostics plus validation as the mitigation; xacml4j can offer the mitigation and the fail-closed switch, which is more than Cedar itself offers (`ErrorHandling` has one variant).

Why D1 rather than D2 as the alternative: D1 reuses XACML's own vocabulary for "I could not evaluate a guardrail" (Indeterminate{D} with `missing-attribute` or `processing-error`), keeps the §7.19.3 resubmission protocol and the deny-biased PEP outcome, and composes correctly under deny-overrides; D2's hard Deny hides the error from the PEP and from XACML parents, which is a worse fit for an XACML PDP than for a standalone Cedar engine.

Why not B: it changes the meaning of every Cedar error, loses determining and erroring sets, makes the corpus and cedar-java unusable as oracles for error cases, and is available anyway to anyone who writes the same policy in XACML or ALFA.

**Risks.**

- Fail-open forbid under A when attribute sources fail (1.7, 2 security); mitigated by D1 for high-assurance deployments, by metrics on erroring forbids, and by an optional refinement listed below (treat PIP transport failures as fail-closed even in A).
- Diagnostics leakage through the first-error global status (2 mixing); needs the scoped-status API before the Cedar algorithm ships.
- Facade mapping: A's NotApplicable inside an XACML policy set means "no Cedar policy applies", not Cedar's Deny; a mixed deployment that expects Cedar's default deny must wrap the Cedar policy set in `deny-unless-permit` at the top level (C.6) or rely on a deny-biased PEP (§7.2.2).
- Oracle drift: cedar-java trails the language (BR2: 4.10.0 against 4.14.0), so error behaviour of new features (schema linking, external declarations) can only be tested against the Lean CLI or the Rust CLI until the binding catches up.
- D1 is a Cedar superset; the corpus must be post-processed and the Lean proofs do not cover it (1.4); it must be documented as "not Cedar".

**What would be BREAKING.**

- A PDP-wide error mode that reaches `Rule.evaluate`, `Condition.evaluate` or the standard algorithms (would change the 66 Indeterminate conformance expectations and the public semantics).
- Any `StatusDetail` on an `ok` status (violates §5.57) or a new `Decision` constant (exhaustive switches; `research/README.md:55-60` already lists `Decision` changes as breaking).
- Changing `addEvaluationResult` or `ReturnPolicyIdList` semantics for XACML policies (conformance case IIIG300 counts policy ids, lane TV3); Cedar determining sets must be recorded in the Cedar diagnostics structure, not by redefining the XACML policy id list.
- Adding a field to `Result` changes `equals` and `hashCode` (`Result.java:54-70`), which is source compatible but affects tests that compare results; a side attachment outside equality avoids it.
- Everything in the recommendation is additive: two algorithm ids, a facade, a diagnostics attachment, a scoped-status method on `EvaluationContext` (an interface change that is breaking only for third-party implementations of `EvaluationContext`, so it should be a default method).

**Open questions for the maintainer.**

1. Default confirmed as A (Cedar exact) with D1 opt-in, or D1 as the default for xacml4j because its users are XACML operators?
2. Should the Cedar algorithm classify errors by cause and fail closed only on infrastructure failures (PIP exceptions, which `PolicyInformationPoint` reports as processing-error) while skipping data errors (missing attribute, type error, overflow) as Cedar does? This hybrid is not Cedar and needs its own oracle rule, but it addresses the attribute-source outage risk directly.
3. Diagnostics channel: Java attachment plus metrics only, or also advice on Permit and Deny and a minor status code on `ok`?
4. Facade shape: expose a Cedar-style `CedarAuthorizer.isAuthorized` returning `{decision, determiningPolicies, erroringPolicies}` beside `PolicyDecisionPoint.decide`, and map NotApplicable to Deny only there?
5. Per-policy-set selection: compiler option, a file-level annotation such as `@xacml.errors("fail-closed")`, or a `CombinerParameter` on the compiled policy (`Policy.java:98-106` supports them)?
6. Should erroring Cedar policies ever appear in the XACML `PolicyIdentifierList`? (Recommendation: no; §5.48 lists "fully applicable" policies only.)

FINAL REPORT (BR5 JMH benchmark engineer lane, read-only research, Claude Fable 5.1)

Summary: Cedar's error semantics are definitional: a policy is satisfied only if it evaluates to `ok true`, erroring policies are collected in `erroringPolicies` and never decide; the Rust engine has a single `ErrorHandling::Skip` mode with a comment that other modes were debated; the authors justify skip-on-error by availability (one bad policy must not deny everything) and leave the erroring-forbid case to diagnostics and validation. After validation only overflow, missing entities and non-literal extension arguments can still error. XACML 3.0 propagates errors as Indeterminate{P/D/DP}, resolves them in the combining algorithms, returns plain Indeterminate with a status the PEP can act on, and expects deny-biased PEPs to deny; xacml4j implements this (`Rule`, `Condition`, `DenyOverrides`, `DefaultPolicyDecisionPoint.createResult`) and 66 conformance responses depend on it.
