**1.2 Policy language (fetched from docs.cedarpolicy.com).**

- Grammar (https://docs.cedarpolicy.com/policies/syntax-grammar.html): `Policy ::= {Annotation} Effect '(' Scope ')' {Conditions} ';'`; `Effect ::= 'permit' | 'forbid'`; `Scope ::= Principal ',' Action ',' Resource`; `Principal ::= 'principal' [(['is' PATH] ['in' (Entity | '?principal')]) | ('==' (Entity | '?principal'))]`; `Action ::= 'action' [('==' Entity | 'in' ('[' EntList ']' | Entity))]`; `Resource` mirrors `Principal` with `?resource`; `Condition ::= ('when' | 'unless') '{' Expr '}'`; `Expr ::= Or | 'if' Expr 'then' Expr 'else' Expr`; `Relation ::= Add [RELOP Add] | Add 'has' (IDENT | STR) | Add 'like' PAT | Add 'is' Path ('in' Add)?`; `Add`/`Mult` over `+ - *`; `Unary ::= ['!' | '-']x4 Member`; `Access ::= '.' IDENT ['(' [ExprList] ')'] | '[' STR ']'`; `Primary ::= LITERAL | VAR | Entity | ExtFun '(' [ExprList] ')' | '(' Expr ')' | '[' [ExprList] ']' | '{' [RecInits] '}'`; `Entity ::= Path '::' STR`; `RELOP ::= '<' | '<=' | '>=' | '>' | '!=' | '==' | 'in'`; `VAR ::= 'principal' | 'action' | 'resource' | 'context'`; reserved `true false if then else in like has is __cedar`; strings use Rust escapes; `PAT` adds `\*`. The production parser is LALRPOP (`grammar.lalrpop`, 16 KB; `/`, `%`, `=` are tokens reserved but unused).
- Data types (https://docs.cedarpolicy.com/policies/syntax-datatypes.html): Bool; String; Long (signed 64-bit, overflow is an evaluation error); Set (heterogeneous sets evaluate, the validator accepts only non-empty homogeneous literals); Record (nested, `r.a` or `r["a"]`); Entity (`Namespace::Type::"id"`); extension types `datetime` (milliseconds since the epoch in a long, normalised to UTC; constructors `"YYYY-MM-DD"`, `...Z`, `...±hhmm`, optional `.SSS`), `decimal` (fixed point, at most 4 fractional digits, range ±922337203685477.5807), `duration` (milliseconds in a long, `"1d2h3m4s5ms"`, negative allowed), `ipaddr` (v4 or v6, optional CIDR). "A policy that results in an error is ignored."
- Operators (https://docs.cedarpolicy.com/policies/syntax-operators.html): `like` glob with `*` and `\*`; constructors `datetime()`, `decimal()`, `duration()`, `ip()` (strict validation requires string literals); `==`/`!=` on any types, false across types (the validator rejects mixed non-entity types); `< <= > >=` on long, datetime and duration; `.lessThan()` etc. on decimal; `&&`, `||` short-circuit; `!`; `if-then-else` (a strict generalisation of `&&` and `||`); `+ - *` on long only, no division, overflow not caught by the validator; `in` (reflexive, transitive, right side an entity or a set of entities, no short-circuit over sets, references to unknown entities are valid and have no ancestors); `has` and extended `e has a.b.c`; `.hasTag(e)`, `.getTag(e)` with computed keys; `is` and `is T in E`; `.contains`, `.containsAll`, `.containsAny`, `.isEmpty`; ipaddr `.isIpv4 .isIpv6 .isLoopback .isMulticast .isInRange`; datetime `.offset(duration) .durationSince(dt) .toDate() .toTime()`; duration `.toMilliseconds .toSeconds .toMinutes .toHours .toDays`.
- Templates (https://docs.cedarpolicy.com/policies/templates.html): placeholders `?principal` and `?resource` only, only in the scope on the right of `==` or `in` (also `is T in ?x`); template-linked policies follow later edits of the template.
- Evaluation (https://docs.cedarpolicy.com/auth/authorization.html): a request is PARC (principal, action, resource entity references; context record). Each policy evaluates to true, false or error. Decision: any satisfied `forbid` gives Deny; else any satisfied `permit` gives Allow; else Deny. Diagnostics carry the determining policy ids and the ids and particulars of erroring policies. Stated properties: default deny, forbid overrides permit, skip on error (chosen over deny-on-error so that one bad policy cannot deny everything). Scope constraints cannot error; conditions are evaluated in order and evaluation stops at the first unsatisfied or erroring clause.
- JSON formats. Policy (https://docs.cedarpolicy.com/policies/json-format.html): `effect`; `principal`/`action`/`resource` with `op` in All, `==`, `in`, `is` plus `entity`, `slot`, `entities`, `entity_type`, `in`; `conditions[{kind, body}]`; `annotations`; expression nodes `Value`, `Var`, `Slot`, `!`, `neg`, `isEmpty`, binary `== != in < <= > >= && || + - * contains containsAll containsAny hasTag getTag`, `.`, `has` (string or path list), `is`, `like` (array of `Wildcard` and `{Literal}`), `if-then-else`, `Set`, `Record`, and any other key is an extension function; policy sets have `staticPolicies`, `templates`, `templateLinks[{templateId, newId, values}]`. Entities (https://docs.cedarpolicy.com/auth/entities-syntax.html): `[{uid:{type,id}, parents:[...], attrs:{...}, tags:{...}}]`, JSON string, integer, boolean, array and object become String, Long, Bool, Set and Record; `__entity` and `__extn{fn,arg}` escapes may be omitted under schema-based parsing; the context record uses the same encoding.
- Validation (https://docs.cedarpolicy.com/policies/validation.html): schema driven; errors for unknown entity types, actions and attributes, actions applied to the wrong principal or resource types, `==` versus `in` misuse, unguarded optional attributes, operator type mismatches, invalid enum ids; warnings for impossible policies, mixed scripts and bidi controls; validation soundness is proved in Lean; not covered are Long overflow, missing entities and extension constructors on non-literal strings in non-strict mode; request validation and schema-based parsing are separate utilities; "the Cedar authorization APIs do not perform validation at the same time that a request is evaluated".
- Formal model (https://github.com/cedar-policy/cedar-spec; https://github.com/cedar-policy/cedar-spec/raw/refs/heads/main/cedar-lean/README.md): `cedar-lean` defines `evaluate`, `satisfied`, `isAuthorized`, `typeOf`, a definitional symbolic compiler (`Cedar/SymCC/`), and proves authorization theorems (`Cedar/Thm/Authorization.lean`), sound policy slicing, sound type checking, sound level-based entity slicing, sound and complete symbolic compilation and verification; `cedar-drt` runs differential random testing against the Rust engine; `cedar-lean-cli` offers `analyze`, `evaluate`, `validate`, `symcc` (analysis needs cvc5 1.0.5 or later). Papers: arXiv:2403.04651 (design, Lean proofs, benchmarks against OpenFGA and Rego) and arXiv:2407.01688 (verification-guided development: 4 validator bugs found by proofs, 21 by DRT and property testing). https://docs.cedarpolicy.com/other/security.html: safe-Rust subset, property tests, DRT.

**1.3 Schema (fetched).**

- Human-readable format (https://docs.cedarpolicy.com/schema/human-readable-schema.html; grammar https://docs.cedarpolicy.com/schema/human-readable-schema-grammar.html): `Schema := {Namespace}`; `Namespace := Annotations 'namespace' Path '{' {Decl} '}' | Decl`; `Entity := Annotations 'entity' Idents ['in' EntOrTyps] [['='] RecType] ['tags' Type] ';' | ... 'enum' '[' STR {',' STR} ']' ';' | Annotations 'external' 'entity' Idents ['in' EntOrTyps] ';'`; `Action := Annotations 'action' Names ['in' RefOrRefs] [AppliesTo] ';' | ... 'external' 'action' ...`; `TypeDecl := Annotations 'type' TYPENAME '=' Type ';'`; `Type := Path | 'Set' '<' Type '>' | '{' [AttrDecls] '}'`; `AttrDecls := Annotations Name ['?'] ':' Type ...`; `AppliesTo := 'appliesTo' '{' ('principal' | 'resource') ':' EntOrTyps ..., 'context' ':' (Path | RecType) '}'`. Documented example: `entity User in [Group] { personalGroup: Group, delegate?: User, blocked: Set<User>, team: Team, } tags String;`, `entity Group enum ["G1", "G2", "G3"];`, `external entity Team in [Organization];`, `action ViewDocument in [ReadActions, ExampleNS::Action::"Write"] appliesTo { principal: [User,Public], resource: Document, context: { network: ipaddr, browser: String } };`. Rules: an action without `appliesTo` applies to nothing (a pure action group); `context` must be a record; common types must be acyclic; name resolution priority is common type, then entity type, then primitive or extension; `__cedar` is reserved (`__cedar::ipaddr`); nothing may shadow the empty namespace; annotations `@doc("...")` are allowed on namespaces, entity types, attributes, actions and common types (RFC 48).
- JSON format (https://docs.cedarpolicy.com/schema/json-schema.html): `{ "<Namespace>": { "entityTypes": { "<T>": { "memberOfTypes": [...], "shape": { "type": "Record", "attributes": { "<a>": { "type": ..., "required": false } } }, "tags": {...}, "enum": [...], "annotations": {...} } }, "actions": { "<a>": { "memberOf": [{"id", "type"?}], "appliesTo": { "principalTypes": [...], "resourceTypes": [...], "context": { "type": "Record", "attributes": {...} } } } }, "commonTypes": {...}, "annotations": {...} } }`; attribute types `String`, `Long`, `Boolean` or `Bool`, `Record`, `Set{element}`, `Entity{name}`, `Extension{name}`, `EntityOrCommon{name}`, or a common type name; built-in extension names `ipaddr`, `decimal`, `datetime`, `duration`.

## 2. Mapping and design options

**2.1 Cedar to XACML 3.0 and to xacml4j (inference grounded in section 1).**

| Cedar construct | XACML 3.0 and xacml4j counterpart | Fidelity |
| --- | --- | --- |
| `permit` / `forbid` policy | `Rule` with Effect Permit or Deny (`Rule.java:41`); a Cedar policy set becomes one `Policy` | direct |
| forbid overrides, default deny, skip on error | nearest standard algorithm is `deny-overrides` plus NotApplicable mapped to Deny at the boundary; but XACML turns errors into Indeterminate and deny-overrides escalates them (`DenyOverrides.java:100-106`) whereas Cedar skips the erroring policy | custom rule-combining algorithm needed (Deny if any Deny, Permit if any Permit, else NotApplicable; Indeterminate counted as NotApplicable; errors kept in `Status`); about 40 lines via the existing annotation registration |
| `principal == T::"id"`, `action == A`, `resource == R` | `Target` with `Match` on subject-id, action-id, resource-id (`Match.java:44-47`) | direct once an entity reference has a canonical value form (string `Type::"id"` or a new `entityRef` type) |
| `principal in G`, `resource in F`, `action in [A1, A2]` | no XACML construct; (a) an `urn:xacml4j:cedar:ancestors` bag attribute per category, closure computed by the entity store or PIP, then `*-is-in` and `*-at-least-one-member-of`; (b) a `cedar:in` function that walks parents through a PIP resolver | (a) is fast and standard-function based; (b) reproduces reflexive `in` on unknown entities |
| `principal is T` | `Match` on an entity-type attribute (`urn:xacml4j:cedar:entity-type`) | direct by convention |
| `when` / `unless` | `Condition`; several clauses become `and(...)`, `unless` becomes `not(...)`; Cedar stops at the first unsatisfied clause and xacml4j's `and` is lazy (`LogicalFunctions.java:65`) | direct |
| `==`, `!=` | type-specific `*-equal`; Cedar yields false across types, XACML raises a type error | needs the schema for static dispatch, or a polymorphic `cedar:equal` function |
| `<`, `<=`, `>`, `>=` | long: `integer-*`; datetime: `dateTime-*`; duration: XACML defines only `dayTimeDuration-equal` (A.3.6, not re-read in this lane: PARTIAL) | engine function for duration ordering |
| `+`, `-`, `*` | `integer-add`, `integer-subtract`, `integer-multiply`; XACML integer is unbounded in the schema, xacml4j's `IntegerVal` is a long (`IntegerVal.java:76`) that wraps, Cedar errors on overflow | checked variants needed |
| `decimal` | XACML `double` loses fixed-point exactness | new `decimal` value type for fidelity |
| `like` | `string-regexp-match` after glob-to-regex translation (escape metacharacters, `\*` literal) through the regex SPI | direct with care |
| `has`, extended `has` | `attribute-designator` with MustBePresent false plus `*-bag-size` greater than 0, or `Entity.hasValues` (`Entity.java:75-80`); optional attributes equal MustBePresent false | direct |
| `.hasTag(k)`, `.getTag(k)` with computed keys | `attribute-designator(entity, keyExpr, type)` already takes the attribute id as a runtime `anyURI` value (`AttributeDesignatorFunctions.java:48-54`) | direct, a close match |
| sets | bags: `.contains` is `*-is-in`, `.containsAll` is `*-subset`, `.containsAny` is `*-at-least-one-member-of`, `.isEmpty` is `*-bag-size = 0`, set equality is `*-set-equals`; nested `Set<Set<T>>` is impossible, bags cannot nest (`BagOfValues.java:52-54`) | direct, except nested sets (wrap in `entity` values or reject) |
| records (nested) | `entity` values (`Entity.java:45-51`) read with `attribute-designator`; sets of records become bags of entities | direct through the Entities profile |
| entities with attrs and parents | principal, resource, action and context map to the access-subject, resource, action and environment categories (`CategoryId.java:43-48`); entities reached through attributes are embedded `entity` values (Cedar level validation, RFC 76, bounds the depth, which matches embedding) or resolved by a PIP keyed by a custom category per entity uid (`CategoryId.java:136-142`); the PIP SPI resolves by category, id, type and issuer only (`PolicyInformationPoint.java:64-66`) | design choice |
| `context` | environment category, or a `cedar:context` category holding one `entity` | direct |
| `if-then-else` | no XACML operator; xacml4j supports lazy parameters (`FunctionSpec.java:108`) | engine function `cedar:if-then-else` |
| ipaddr methods | XACML `ipAddress` is address, mask and port range (`IPAddress.java:45-46`), CIDR semantics differ; the only standard ipAddress predicate is `ipAddress-regexp-match` | engine functions |
| datetime methods | `.offset` is `dateTime-add-dayTimeDuration`; `.durationSince`, `.toDate`, `.toTime` have no standard function; Cedar normalises to UTC milliseconds, XACML keeps offsets | partial |
| templates | no counterpart; expand each template link into a static `Policy` whose id is the link id; re-expand when the template changes | static expansion |
| annotations | `Description` and metadata; `@id` becomes the policy id | direct |
| obligations, advice | absent in Cedar; a superset convention such as `@xacml.obligation("urn:...")` stays a valid Cedar policy because Cedar ignores annotations | superset only |
| diagnostics | determining policies are the ReturnPolicyIdList policy references (`RequestContext.java:98-110`, `Result.java:50`); errors go to `Status`; Cedar Deny with no determining policy is XACML NotApplicable, Cedar Allow is Permit | direct at the boundary |
| validation | xacml4j checks function signatures and condition types at build time (`Match.java:58-74`, `Condition.java:58-63`, `FunctionSpec.java:116-126`) but has no attribute schema | the schema adds attribute-level validation: the authorization model |

**2.2 Question 1, Cedar policy support in xacml4j.** Options, with trade-offs. Effort figures are rough inferences.

- Option A, Cedar front end compiled to the xacml4j policy model. New module `xacml-cedar` depending on `xacml-core` and `xacml-pdp`: `org.xacml4j.cedar.parser` (ANTLR4 grammar `Cedar.g4` transcribed from the Apache-2.0 grammar page, or a hand-written recursive-descent parser with a Pratt expression parser; ANTLR4's runtime is BSD-3-Clause), `org.xacml4j.cedar.ast` (records for policies, scope constraints, expressions, templates), `org.xacml4j.cedar.compile` (AST to `Policy`, `Rule`, `Target`, `Condition`, `Apply` through the existing builders), `org.xacml4j.cedar.functions` (`@XacmlFunctionProvider` with ids `urn:xacml4j:names:cedar:1.0:function:{in,like,if-then-else,equal,duration-less-than,datetime-duration-since,datetime-to-date,datetime-to-time,ip-is-in-range,...}`), `org.xacml4j.cedar.combine` (`urn:xacml4j:names:cedar:1.0:rule-combining-algorithm:forbid-overrides`), `org.xacml4j.cedar.entities` (Cedar entity JSON to request categories, ancestor closure, a PIP resolver), and a `MarshallingProvider` for `text/cedar` and the Cedar policy JSON. Pros: one evaluator and one PDP, so the JMH and allocation work of `optimize-pdp-evaluation` applies; obligations and advice remain available through the annotation superset; XACML requests, responses and audit stay unchanged; everything plugs into existing annotation-driven extension points. Cons: semantic drift risk, because Cedar's semantics are formally specified and the compiler must reproduce skip-on-error, reflexive and transitive `in`, polymorphic `==`, overflow errors, set equality that ignores duplicates, string escapes and glob matching; constructs without a faithful mapping (if-then-else with non-boolean branches, nested sets, decimal, duration ordering, datetime arithmetic) need engine-specific functions and types, which makes a "Cedar on XACML" dialect; the front end must track roughly three language releases a year; it cannot run the Lean oracle directly.
- Option B, a separate Cedar evaluator on a shared authorization model. `xacml-cedar` with its own AST interpreter mirroring the Lean definitions (`evaluate`, `satisfied`, `isAuthorized`) over xacml4j's `Value`, `ValueType`, `BagOfValues`, `Entity` and the PIP, plus a `PolicyDecisionPoint` adapter for XACML requests. Pros: faithful semantics, directly testable by differential testing against cedar-java and the Lean CLI; no dialect; the type-system work (ValueBox, Valhalla) is shared. Cons: two evaluators and two policy models to maintain; no obligations or advice unless Cedar is extended; XACML functions cannot appear in Cedar expressions because the operator set is closed; perf work must be done twice; the shared model still needs the Cedar-only types (decimal, entity references, nested sets).
- Option C, interop through cedar-java. A thin `xacml-cedar-bridge` module exposing `PolicyDecisionPoint` by converting `RequestContext` to `AuthorizationRequest` plus `Entities` and back. Pros: zero semantic risk, about one to two thousand lines, immediate schema validation, templates, level validation and the experimental partial evaluation; Apache-2.0 is compatible with LGPL v3. Cons: a JNI native library inside an otherwise pure-Java library (Linux and macOS in the uber jar, Windows unsupported, GraalVM native-image friction, no benefit from the JDK 28 value-class plan); cedar-java lags the language (4.10.0 versus 4.14.0, language 4.5 versus 4.6, and the project skipped 4.4 to 4.7); lossy conversions between bags and sets, `dateTime` with offsets and UTC `datetime`, `ipAddress` with ports and CIDR `ipaddr`, unbounded integer and long; no obligations.
- Option D, do not do it. Publish a sample project that runs cedar-java beside xacml4j and spend the effort on the authorization model (2.3) and ALFA (lane BR1). Pros: no new modules, no drift, no native code. Cons: Cedar users get nothing from xacml4j; the maintainer's goal is unmet.

**2.3 Question 2, Cedar schema syntax as xacml4j's authorization-model language.**

- Option S1, adopt the Cedar schema formats verbatim and carry XACML-only metadata in annotations. Files stay valid Cedar schemas that the Cedar CLI and Verified Permissions can validate; xacml4j reads the same files plus annotations such as `@xacml.category("urn:oasis:names:tc:xacml:1.0:subject-category:access-subject") entity User {...}`, `@xacml.attributeId("urn:oasis:names:tc:xacml:1.0:subject:subject-id") id: String`, `@xacml.issuer(...)`, `@xacml.type("x500Name")` on a `String` attribute. Mapping: entity type to category plus entity-type attribute; attribute to attribute id with data-type mapping (String to string, Long to integer, Bool to boolean, `Set<T>` to a bag of T, Record to `entity`, Entity to an entity reference, datetime to dateTime, duration to dayTimeDuration, decimal to double or a new decimal, ipaddr to ipAddress); `?` to MustBePresent false; `in [Group]` to the hierarchy; `tags T` to an open attribute set of one type; `appliesTo` to the categories a request may carry per action; `context` to environment attributes; common types to shared record shapes; the 4.14 `external` and schema linking features make "default XACML 2.0 model" and "default XACML 3.0 model" shippable as fragments (`external entity Subject;` in an application schema, linked to the xacml4j fragment that defines the standard categories and attribute ids). Pros: proven, documented, two formats, tooling and editors already exist, annotations are first-class since RFC 48. Cons: Cedar's PARC model is narrower than XACML categories (several subjects, codebase, intermediary, delegate), issuers and MustBePresent-per-use do not exist, functions are not declarable (XACML's open function registry needs its own section or stays implicit in `XacmlDefaultFunctions`), obligation and advice ids with their assignment shapes are not expressible, and XACML data types without Cedar equivalents (x500Name, rfc822Name, dnsName, hexBinary, base64Binary, yearMonthDuration, date, time, xpathExpression) must be encoded as annotated primitives, which Cedar validators then type as String.
- Option S2, an xacml4j-owned model DSL (ALFA-like, lane BR1) with Cedar schema import and export adapters. Pros: XACML-complete, no divergence from Cedar tools because export covers only the common subset. Cons: a new syntax to design, document and parse; two syntaxes to keep aligned.
- Option S3, Cedar JSON schema only as an exchange format with extra keys. Rejected: unknown keys are errors in the current JSON schema format (only the deprecated 2.5-compatibility parser ignores them), so extended files stop validating.
- Option S4, do nothing: keep attribute knowledge in `@XacmlAttributeResolverDescriptor` resolver descriptors (`XacmlAttributeResolverDescriptor.java:32-40`). Pros: zero cost. Cons: no policy validation against a model, no generated documentation, no ALFA or Cedar bridge.

**2.4 Recommendation.** Do S1 first, then A in stages, with cedar-java only as a test oracle; do not do B or C as product code.

- Why S1 first: it is the highest-value, lowest-risk piece and pays for XACML itself. A schema lets xacml4j validate `AttributeDesignator` ids and types at policy load, generate documentation, and seed both the ALFA work and the Cedar front end. Annotations keep the files valid Cedar, which preserves the Cedar tooling and Verified Permissions compatibility the maintainer asked for. Ship the XACML 2.0 and 3.0 default models as linkable fragments.
- Why A over B and C: one evaluator keeps the measured PDP path and the type-system investment in one place; obligations and advice stay available; the custom combining algorithm, engine functions and media types all fit existing annotation-driven extension points without touching the core. Gate it: phase 1 parser and AST with a formatter round-trip; phase 2 compiler restricted to schema-validated input with an explicit unsupported list (nested sets, non-boolean `if-then-else`, decimal arithmetic until a decimal type exists); phase 3 differential tests against cedar-java (test scope only) and the Cedar integration corpora, plus the JMH harness.
- Why not C in product code: JNI in an LGPL pure-Java library, unsupported Windows, a lagging binding and lossy type conversion make it a demo, not an engine feature.

## 3. Risks, breaking changes, open questions

**3.1 Risks.**

- Semantic fidelity: polymorphic `==`, `in` on unknown entities, set-versus-multiset equality, Long overflow, UTC normalisation, decimal precision, glob translation and the first-unsatisfied-clause order each need a test derived from the docs or the Lean model; the Lean theorems do not transfer to a compiled XACML form.
- Release cadence: four Cedar language versions in eighteen months; cedar-java trails by one language version and skipped four releases, so an oracle pinned to cedar-java cannot test the newest features (external declarations, schema linking).
- Error model: Cedar skip-on-error inside xacml4j must stay confined to the Cedar combining algorithm; making it global would break the OASIS conformance cases that expect Indeterminate (lane TV3 inventory: `IIC`/`IID` families).
- Entity data volume: Cedar passes the entity store with each request; embedding related entities as `entity` values grows request size, and a PIP-based variant needs a per-request cache keyed by entity uid.
- Licensing: all Cedar artefacts are Apache-2.0 (section 1.1); vendored grammar text or corpora need Apache attribution and NOTICE lines; "Cedar" is a CNCF project name, so module names should be descriptive (`xacml-cedar`) and not imply endorsement.
- Tooling: an ANTLR4 grammar is the only maintained-grammar path with a Java target; the community MIT grammar is a 4-commit JavaScript project; the LALRPOP source is Rust-only but is the reference for precedence.

**3.2 What would be BREAKING.**

- Not breaking if done as new modules plus new identifiers: `xacml-cedar` module, `urn:xacml4j:names:cedar:1.0:*` functions and the combining algorithm, a `cedar:context` category, annotation conventions, an authorization-model module.
- Adding constants to the `MediaType` enum (`MediaType.java:48-60`) or the `XacmlTypes` enum (`XacmlTypes.java:42-162`) is source compatible but changes `values()` and breaks exhaustive switches; replacing either enum by an open registry is a BREAKING public API change.
- Changing `Decision` to carry diagnostics, changing `Rule` or `Condition` error semantics, or letting `BagOfValues` nest (`BagOfValues.java:52-54`) is BREAKING and would alter conformance results; keep diagnostics in `Status` and policy references, and keep nesting inside `entity` values.
- A new `decimal` or `entityRef` value type is additive, but `ValueType.ofAny` parsing and the JSON and XML marshallers must learn the new ids, which touches `xacml-xml` and `xacml-json`.
- A cedar-java dependency in `test` scope only affects CI (native library on Temurin Linux); in `compile` scope it would be a dependency and platform change that needs an OpenSpec change under the project rules.

**3.3 Open questions for the maintainer.**

1. Target Cedar language version and feature cut: 4.6 as of 2026-10-17; are templates, enumerated entity types, tags, level validation and the experimental partial evaluation in or out?
2. Error model: is a Cedar-specific skip-on-error combining algorithm acceptable, or must Cedar errors surface as XACML Indeterminate?
3. Obligations and advice for Cedar policies: an annotation superset, or none?
4. Entity data: passed per request as embedded `entity` values (Cedar style) or resolved through the PIP (XACML style)? Who computes the ancestor closure?
5. New data types: add `decimal` and an entity-reference type to `XacmlTypes`, or keep them in a Cedar-local type registry? How does this interact with the Valhalla value-class migration?
6. Is a JNI dependency (cedar-java, Apache-2.0) acceptable in test scope as a differential oracle, and on which CI platforms?
7. Which document defines the "XACML 4.0 model" named in the request? The OASIS TC now operates as ACAL and no 4.0 core specification was found in this lane (UNVERIFIED); lanes BR1 and BR3 should confirm.
8. Should authorization-model files be valid Cedar schemas with `@xacml.*` annotations (S1) or an xacml4j syntax with Cedar import and export (S2)? If S1, which annotation names and which default fragments (2.0, 3.0, profiles) ship with the engine?
9. Should policy media types for `text/cedar` and Cedar JSON extend the `MediaType` enum now, or wait for a registry refactor?
