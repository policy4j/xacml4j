## Suggested adoption sequence

1. **Compare before importing.** Match policy, request, response and special setup against the 880 existing manifest identities. Record the upstream URL, revision, original license and any local adaptation for each genuinely new case.
2. **Pilot Curity and the Go IAM assertions.** They provide small, explicitly licensed examples with stated outcomes. Recheck the expected decisions against the standard and compare complete response fields where the source supplies them.
3. **Add profile tests by capability.** Start with JSON serialization and multiple-decision cases; keep REST/SAML transport, GeoXACML, hierarchical resources and custom resolvers in separately identified capability groups. Existing suite indexes already cover some of these topics.
4. **Keep rejection and convention cases explicit.** Do not turn an engine’s parser rejection, clock override, policy-reference treatment or response-order convention into an OASIS requirement without checking the applicable standard section.

No files were written, no sign-in was attempted, and no tests or benchmarks were run. Counts, licenses and overlaps marked unverified remain research gaps.
