2: 
3: OpenSpec holds the plan, the requirements, and the proof for every
4: non-trivial change. This file is the procedure. `openspec/config.yaml` holds
5: the compact rules that the OpenSpec CLI injects into generated instructions.
6: 
7: ## When to use it
8: 
9: Use a change for new capabilities, behavior changes (XACML semantics,
10: marshalling, PDP), public API or type-system changes, dependency, build, or
11: JDK changes, and any multi-step work. Skip it for a typo, a comment, or a
12: local fix with no behavior change; still run the tests.
13: 
14: ## Schema
15: 
16: The project schema is `policy4j-spec-driven`
17: (`openspec/schemas/policy4j-spec-driven/`). Artifacts, in dependency order:
18: 
19: | Artifact | File | Purpose |
20: | --- | --- | --- |
21: | proposal | `proposal.md` | Why, what changes, capabilities, research questions, verification, impact, beads epic |
22: | research | `research/README.md` | REQUIRED or NOT REQUIRED; answers with sources; swarm lane index |
23: | specs | `specs/<capability>/spec.md` | Normative SHALL/MUST requirements with GIVEN/WHEN/THEN scenarios |
24: | design | `design.md` | Decisions D1..Dn, test strategy, benchmark plan, execution plan (swarm lanes), risks |
25: | tasks | `tasks.md` | `- [ ] X.Y` checklist; X.Y maps to beads issue `<epic>.X.Y` |
26: | evidence | `evidence/README.md` | Requirement → test → run index; gate tasks → runs |
27: 
28: `apply` needs tasks and evidence. Check progress with
29: `openspec status --change <id>`; print the generated instructions for one
30: artifact with `openspec instructions <artifact> --change <id>`.
31: 
32: ## Lifecycle
33: 
34: 1. **Explore** (optional). Read AGENTS.md, `openspec list --specs`, and the
35:    code (`ripwire . --for="<goal>"`). No files yet.
36: 2. **Propose.** Create the change with a verb-led kebab-case id and write
37:    the artifacts in order. Planners can be a single agent or a planning
38:    swarm (docs/ai/SWARMS.md).
39: 3. **Validate.** `openspec validate <id> --strict` must pass.
40: 4. **Review the plan.** At least one architecture reviewer lane that did not
41:    write the plan (for example `policy4j_arch_review_*`). Record the review
42:    under `evidence/reviews/plan/`.
43: 5. **Approve.** The maintainer approves the change. No implementation
44:    before approval.
45: 6. **Track.** Create the beads epic and one issue per task
46:    (docs/ai/BEADS.md). Put the epic id in `proposal.md` (Tracking) and the
47:    `tasks.md` header.
48: 7. **Apply.** One task group at a time (below).
49: 8. **Verify.** Every checked task has an indexed run; every requirement maps
50:    to a passing test or conformance case; `openspec validate <id> --strict`
51:    passes.
52: 9. **Archive.** After the maintainer lands the work:
53:    `openspec archive <id> --yes`, then `openspec validate --all --strict`.
54:    Archiving merges the spec deltas into `openspec/specs/`.

1: ## ADDED Requirements
2: 
3: ### Requirement: Verify provider readiness and scope
4: 
5: The workflow SHALL check the selected desktop application's installed identity,
6: version, local permissions, usable window, research controls, and account
7: readiness before submission. It SHALL report unavailable or incomplete coverage
8: and SHALL NOT silently substitute ordinary chat, an API, or a web browser.
9: 
10: #### Scenario: Readiness succeeds
11: - **GIVEN** the selected desktop app exposes usable research controls
12: - **WHEN** readiness is checked
13: - **THEN** the result identifies the app, version, permissions, and research-mode evidence
14: - **AND** no prompt is submitted by the readiness check
15: - **Test:** `test_doctor_reports_observed_capabilities`; live `provider_readiness`.
16: 
17: #### Scenario: Research controls or permissions are unavailable
18: - **GIVEN** a required permission, window, sign-in, or research control is missing
19: - **WHEN** a submission is requested
20: - **THEN** the job records the specific blocked state and no prompt is sent
21: - **Test:** `test_start_blocks_without_research_readiness`.
22: 
23: ### Requirement: Submit only to an identified research conversation
24: 
25: The workflow SHALL use a new dedicated conversation, preserve existing drafts,
26: verify target focus and selected research mode before input, and associate the
27: submitted question with a unique local job marker and observed conversation
28: identity. It SHALL record submission intent before sending and SHALL distinguish
29: an attempted send from an observed provider receipt.
30: 
31: #### Scenario: Observed research submission
32: - **GIVEN** readiness succeeds and a bounded question is authorized
33: - **WHEN** the workflow submits it in a dedicated research conversation
34: - **THEN** the saved receipt matches the question marker and observed conversation
35: - **AND** the selected mode is ChatGPT Deep Research or Claude Research as requested
36: - **Test:** `test_start_requires_observed_receipt`; live `research_submission` for both providers.
37: 
38: #### Scenario: Draft or focus changes before input
39: - **GIVEN** an existing draft or changed foreground target is detected
40: - **WHEN** the workflow is preparing or entering a question
41: - **THEN** it preserves the draft, stops input, and records an actionable interruption
42: - **Test:** `test_focus_change_preserves_draft_and_stops_input`.
43: 
44: ### Requirement: Handle provider interaction states explicitly
45: 
46: The workflow SHALL distinguish preparation, submission uncertainty, clarifying
47: questions, proposed plans, active research, provider completion, quota/error
48: states, and incomplete collection. It SHALL follow a proposed plan only within
49: the authorized question and source scope, and SHALL stop for questions or scope
50: expansion that cannot be answered from the authorized inputs.
51: 
52: #### Scenario: Plan remains within the authorized scope
53: - **GIVEN** the provider proposes a plan within the question and allowed sources
54: - **WHEN** the workflow evaluates the plan
55: - **THEN** it can begin research and records the observed transition
56: - **Test:** `test_authorized_plan_can_start_research`.
57: 
58: #### Scenario: Provider needs an unprovided choice
59: - **GIVEN** the provider asks a question or adds a source outside the authorized scope
60: - **WHEN** status is observed
61: - **THEN** the workflow records the pending interaction and does not invent a reply
62: - **Test:** `test_unresolved_question_or_plan_scope_stops`.
63: 
64: #### Scenario: Provider quota is exhausted
65: - **GIVEN** the provider shows a quota or subscription limitation
66: - **WHEN** status is observed
67: - **THEN** the job records that provider outcome without repeated submission or upgrade actions
68: - **Test:** `test_quota_state_does_not_resubmit`.
69: 
70: ### Requirement: Resume observations without duplicate submission
71: 
72: The workflow SHALL persist jobs atomically and resume status checks against the
73: same observed conversation. An observation timeout, script exit, or missing
74: local process SHALL NOT itself establish provider failure or permit resubmission.
75: After an uncertain send, it SHALL reconcile provider state before another send.
76: 
77: #### Scenario: Wait expires while research continues
78: - **GIVEN** an identified research job remains active
79: - **WHEN** a bounded wait expires and the command is later resumed
80: - **THEN** it re-observes the same job and retains the recorded provider state
81: - **AND** it does not send the question again
82: - **Test:** `test_wait_timeout_preserves_job_and_resume_does_not_submit`; live `timeout_resume`.
83: 
84: #### Scenario: Process stops after sending but before receipt persistence
85: - **GIVEN** submission intent was saved and the process stops at an uncertain send
86: - **WHEN** the job is resumed
87: - **THEN** matching provider evidence recovers the receipt or the job remains uncertain
88: - **AND** no automatic duplicate is submitted
89: - **Test:** `test_crash_after_send_requires_reconciliation`.
90: 
91: ### Requirement: Serialize desktop actions and isolate job data
92: 
93: The workflow SHALL allow only one mutating desktop action at a time across
94: processes and checkouts. Batch execution SHALL queue jobs in declared order and
95: retain an independent outcome per provider. Inspections and evidence SHALL be
96: limited to the selected job, and default diagnostics SHALL redact conversation
97: text, prompts, account data, and unrelated clipboard contents.
98: 
99: #### Scenario: Concurrent commands contend for desktop ownership
100: - **GIVEN** a process owns an active desktop action
101: - **WHEN** another process requests input or collection
102: - **THEN** it waits within a bound or returns a clear busy outcome without GUI input
103: - **Test:** `test_desktop_lock_serializes_processes`.
104: 
105: #### Scenario: One batch provider is blocked
106: - **GIVEN** a batch targets both providers and one lacks research availability
107: - **WHEN** the batch executes
108: - **THEN** the other provider can proceed and each job keeps its own result
109: - **AND** a partial batch is not reported as fully collected
110: - **Test:** `test_batch_preserves_per_provider_outcomes`.
111: 
112: #### Scenario: Diagnostic inspection sees unrelated data
113: - **GIVEN** the selected app contains unrelated chats or clipboard contents
114: - **WHEN** a readiness check or diagnostic inspection runs
115: - **THEN** logs retain only capability flags, allowlisted controls, and job metadata
116: - **Test:** `test_default_diagnostics_redact_unrelated_data`.

DOCUMENT openspec/changes/add-desktop-deep-research/specs/desktop-research-collection/spec.md
1: ## ADDED Requirements
2: 
3: ### Requirement: Establish provider completion before collecting
4: 
5: The workflow SHALL collect only the completed final research result from the
6: identified job. Stable text, a timer, a Copy button, or an ordinary chat reply
7: alone SHALL NOT establish research completion.
8: 
9: #### Scenario: Identified final research report is ready
10: - **GIVEN** the same job has provider-specific final-result evidence and no pending research interaction
11: - **WHEN** collection begins
12: - **THEN** the receipt records the completion evidence for that job
13: - **Test:** `test_collect_requires_identified_final_research_result`; live `provider_completion` for both providers.
14: 
15: #### Scenario: Research or a clarification is still pending
16: - **GIVEN** the provider is still researching or awaiting a plan/question response
17: - **WHEN** collection is requested
18: - **THEN** it reports incomplete state and does not label partial content as a final report
19: - **Test:** `test_collect_rejects_in_progress_or_pending_interaction`.
20: 
21: ### Requirement: Save cited reports and supported exports with integrity
22: 
23: The workflow SHALL save a nonempty report, source URLs, collection method,
24: provider and app identity, job marker, timestamps, and content hashes. It SHALL
25: preserve supported native exports and identify copied or extracted text by its
26: actual format. It SHALL verify each saved file independently before recording
27: the job as collected.
28: 
29: #### Scenario: Native report export succeeds
30: - **GIVEN** a completed report exposes a supported download format
31: - **WHEN** the export is collected
32: - **THEN** the workflow verifies the completed file, content type, source links, job identity, and hash
33: - **AND** it records only the formats actually saved
34: - **Test:** `test_native_export_is_complete_and_hashed`; live `native_export` when exposed.
35: 
36: #### Scenario: Report-specific Copy or extraction succeeds
37: - **GIVEN** the identified final report exposes Copy or isolated response extraction
38: - **WHEN** the workflow collects that report
39: - **THEN** it binds the result to the job and saves cited Markdown or accurately labeled plain text
40: - **AND** it rejects preexisting clipboard content and incomplete citation extraction
41: - **Test:** `test_copy_collection_rejects_stale_clipboard_and_missing_sources`; live `report_collection` for both providers.
42: 
43: #### Scenario: Export fails after research completes
44: - **GIVEN** provider completion was observed but file validation fails
45: - **WHEN** collection ends
46: - **THEN** the job retains provider completion and records collection failure
47: - **AND** retrying collection does not start another research job
48: - **Test:** `test_failed_export_keeps_provider_completion`.
49: 
50: ### Requirement: Maintain resumable local report storage
51: 
52: The workflow SHALL store each job in a separate local directory with atomic
53: metadata and an index. Default generated prompts, screenshots, and reports
54: SHALL be ignored by Git and readable only by the local user. Collection SHALL
55: reject path traversal and unexpected symbolic links, preserve existing files,
56: and verify hashes when reporting an existing collected result.
57: 
58: #### Scenario: Two provider reports are collected
59: - **GIVEN** two identified provider jobs complete and collect successfully
60: - **WHEN** their local index is read
61: - **THEN** it lists separate reports, sources, receipts, and collection results
62: - **Test:** `test_index_keeps_reports_separate`; live `dual_provider_collection`.
63: 
64: #### Scenario: Existing report is changed or an unsafe output is requested
65: - **GIVEN** saved content no longer matches its hash or an output path escapes the chosen run directory
66: - **WHEN** the workflow reports or writes collection results
67: - **THEN** it reports integrity failure or rejects the unsafe destination without overwriting user files
68: - **Test:** `test_tampered_report_and_unsafe_output_are_rejected`.
