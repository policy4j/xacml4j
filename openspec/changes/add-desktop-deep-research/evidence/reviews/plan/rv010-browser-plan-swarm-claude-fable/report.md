Findings, most severe first.

1. HIGH. design.md D14 "How it is given" (lines 695-715); spec `browser-research-session` requirement "Require the operator's acknowledgement" and scenarios "A receipt is written directly into the store", "A pseudo-terminal is used"; tasks 5.6, 5.7. The design needs "a key that the system releases only after that authentication", which on macOS means a Secure Enclave or data-protection keychain key with a user-presence constraint. Apple DTS answers on the developer forums (threads 728150, 759481, 714752, 793977) say such keys need restricted entitlements authorised by a provisioning profile, and a bare command-line tool has nowhere to carry one; `SecKeyCreateRandomKey` fails with -34018. The helper of D2 is compiled locally into a cache and is at best ad-hoc signed, so the planned 5.6 design is infeasible as written (secondary source, not tested here). The spec still promises the property unconditionally. The threat model is also inconsistent: the signature only stops a forged receipt file, yet D14 declares an agent that "rewrites local files" out of scope. Ask: decide in 5.2, not in 5.6. Either (a) device-owner authentication at the start of every gated command, a plain receipt, and the forged-receipt scenario removed; or (b) a Developer ID signed helper app bundle, which is a new build and signing dependency with its own approval.

2. HIGH. design.md D14 "one rule for both surfaces" (lines 681-682, 670) against the specs and tasks. The acknowledgement requirement exists only in `browser-research-session`, titled "for live browser operations"; `desktop-research-execution` has no acknowledgement or terms text (`rtk rg`, no match), and tasks 2.3, 2.4, 4.1, 4.2 do not mention the gate. D14 says nothing runs live on either surface before the policy is set, while desktop live runs of task 1.4 already happened under the approval of 2026-10-04, which did not raise terms. Ask: either a MODIFIED requirement in the desktop spec with tests, and 4.1/4.2 depending on 5.2, or an explicit statement that the desktop surface stays ungated and why. Tell the maintainer the earlier approval was given without the terms question.

3. MEDIUM. D14 receipt contents (lines 699-700); spec requirement sentence "SHALL record the provider, the address and hash of the terms text and the date". The receipt is not bound to the account, the OS user, or the terms variant. Attack: the operator acknowledges for a personal account; later a work or Team account is signed in to the dedicated profile; every gated operation still verifies; the risk now falls on an account whose holder never acknowledged, under other terms. The variants are real: OpenAI's page says EEA, Switzerland and UK users are under other terms and Business Terms govern Enterprise; Google's page is a "Country version: United States" text; Anthropic's page does not say which terms cover organisation-linked accounts. Ask: record D11's salted account hash and the terms variant in the receipt; a different account hash at the readiness probe gives `TERMS_ACKNOWLEDGEMENT_REQUIRED`; add the scenario.

4. MEDIUM. D14 "current acknowledgement" and "changed terms text" (lines 681-693); spec scenario "The terms text has changed". A changed text never blocks, so "current" means "exists". The hash also needs a fetch the provider permits: openai.com answered HTTP 403 to a plain fetch today, and the research itself read only about half of the Anthropic and Google pages (sources.md "Limits"). A standard-library fetch inside `doctor --local` will fail or hash another rendering, and the command named "local" needs the network. Ask: define current (re-acknowledge before a new job once the hash changes, or an age limit); define the fetch, with failure reported as unverified and never as changed; hash normalised text; document the network access.

5. MEDIUM. D14 "What an acknowledgement is" (lines 672-676) and "An agent process cannot answer that dialog" (698-699). Device-owner authentication proves that someone who can unlock this macOS account answered a dialog that the agent may have started; it shows no terms text, so it proves neither reading nor account holdership, and the operator sees only the reason string. Ask: the command opens or prints the terms address, the dialog reason names provider, terms date and hash, the receipt says "authenticated acknowledgement" rather than "read", and a withdraw command exists. State that the password path holds only because the agent lacks the password.

6. LOW. D14 gated list (lines 683-689). `inspect --job --job-content` reads local files and should not be gated; `batch` with several providers must be gated per entry before that entry's driver starts; "pseudo-terminal" is a misnomer once the gate is OS authentication.

7. LOW. D14 provider paragraphs (649-668) omit two clauses that Q8 quotes and that matter here: Anthropic "crawl, scrape, or otherwise harvest" (covers collection) and OpenAI "circumvent any rate limits … bypass any protective measures" (the clause that D11's no-evasion rule answers). Add both.
